## Yang gugur (kabar baik)

- **Baseline serial nyata.** Ada `fsrcnn_serial` (big core pinned) dan `fsrcnn_serial_little`, dan analisis speedup memakai `serial_idx`, bukan OpenMP 8-thread. Keberatan saya soal "speedup salah kelas" tidak berlaku.
- **Skenario noise sudah proper** dengan `noise_generator` 4 dan 10 thread, cocok dengan Tabel VIII.
- **CFS baseline benar** — binary sama, `SYNCPILOT_DISABLE_AFFINITY=1`, jadi perbandingannya adil.
- **Ada skenario NAIVE** untuk mereplikasi race condition [14]. Ini bagus dan sayangnya belum muncul di paper — padahal itu bukti langsung untuk Section VI-C, bukan sekadar rujukan ke [14].

## Yang terkonfirmasi (harus diperbaiki)

### 1. Bug rata-rata masih ada, dan sekarang pasti masuk ke paper

```bash
avg_time=$((total_time / NUM_RUNS))     # dibagi 8, bukan 7
```

Run pertama (yang script Anda sendiri labeli `Profil`) ikut masuk rata-rata. Paper menyatakan sebaliknya. Rekonstruksi untuk SyncPilot-4W:

- Laporan 3016 ms = (12342 + 7×steady) / 8
- ⟹ steady ≈ **1684 ms**, speedup ≈ **6.2×**, bukan 3.46×

Efeknya paling besar di 4W (karena run profiling paling lama) dan mengecil di 20W. Artinya **kurva scaling Anda terdistorsi secara sistematis** — 4W terlihat jauh lebih buruk dari sebenarnya, sehingga "scaling ke 20W" tampak lebih dramatis dari kenyataannya.

Perbaikan:
```bash
if [ "$run" -eq 1 ]; then
    first_run_time=$elapsed
else
    total_time=$((total_time + elapsed))
    [ $elapsed -lt $min_time ] && min_time=$elapsed
    [ $elapsed -gt $max_time ] && max_time=$elapsed
fi
...
avg_time=$(( total_time / (NUM_RUNS - 1) ))
```

Perhatikan `min_time`/`max_time` juga harus mengecualikan run 1.

### 2. `TIMES_MAX` = cold start, bukan jitter

Ini yang paling merusak, karena mengenai temuan sentral paper Anda.

`max_time` mencakup run 1. Untuk semua skenario, run 1 hampir pasti yang terlama (cold page cache, 15 file bobot, input dibaca dua kali). Jadi kolom "Worst-Case Run (ms)" di Tabel VIII kemungkinan besar melaporkan **cold-start latency**, bukan degradasi akibat noise.

Konsekuensinya: angka 1171→1427 (21.9%) vs 1067→1769 (65.8%) mungkin sebagian besar mengukur perbedaan cold-start, bukan robustness terhadap noise. Karena inilah klaim utama paper, ini harus dipastikan sebelum submit.

Cek cepat: lihat output mentah skenario `D_NOISE_BRUTAL` — apakah run 1 adalah nilai tertinggi dari 8?

### 3. Ground truth masih dari OpenMP paralel

```bash
"${SCRIPT_DIR}/fsrcnn_baseline" "$INPUT_PATH" "$GROUND_TRUTH"    # -fopenmp
```

Anda punya `fsrcnn_serial` yang deterministik, tapi ground truth tetap dibuat dari binary OpenMP. Ini melemahkan klaim korektnes tepat di titik yang Anda tekankan — Anda membuktikan "bebas race condition OpenMP" dengan membandingkan terhadap output OpenMP.

Satu baris:
```bash
"${SCRIPT_DIR}/fsrcnn_serial" "$INPUT_PATH" "$GROUND_TRUTH" "$TOTAL_FRAMES"
```

Ini juga menguatkan skenario NAIVE — kalau NAIVE berbeda dari ground truth serial, Anda punya bukti race condition yang bersih.

## Masalah baru dari script ini

### 4. Noise generator tidak berjalan selama yang Anda kira

```bash
"${SCRIPT_DIR}/noise_generator" $NOISE_THREADS > /dev/null 2>&1 &
NOISE_PID=$!
sleep 2
```

Kalau `noise_generator` punya durasi terbatas dan bukan loop tak-hingga, ia bisa mati di tengah 8 run (total ~10 detik untuk 20W). Run-run belakangan lalu berjalan **tanpa noise sama sekali** — dan itu justru akan menekan rata-rata, menyembunyikan efek yang ingin Anda tunjukkan.

Verifikasi: tambahkan `ps -p $NOISE_PID` setelah loop, atau jalankan `pidstat` paralel. Kalau `noise_generator.c` memang tak-hingga, aman.

Terkait: `kill -9 $NOISE_PID` hanya membunuh proses induk. Kalau ia mem-fork, thread anak bisa bertahan dan mencemari skenario berikutnya. Lebih aman `kill -9 -$NOISE_PID` dengan process group, atau `pkill -f noise_generator`.

### 5. Skenario NAIVE punya perlakuan berbeda

```bash
elif [ "$runner" = "naive" ]; then
    OMP_NUM_THREADS="$workers" "${SCRIPT_DIR}/fsrcnn_naive_openmp" ... "$TOTAL_FRAMES"
```

Tanpa `> /dev/null 2>&1`. Semua skenario lain outputnya dibuang. NAIVE menulis ke terminal, yang menambah waktu I/O — jadi angkanya tidak sebanding.

### 6. `SCENARIO_WORKERS=150` untuk serial

Untuk runner `serial`, nilai 150 tidak dipakai (script meneruskan `$TOTAL_FRAMES`). Tidak berbahaya, tapi membingungkan — dan di script kedua, kolom `Speedup` untuk baris SER akan menampilkan angka worker yang menyesatkan kalau ada yang membacanya.

### 7. Dua script, satu file data

Keduanya bernama `comparison.sh` dan menulis ke `benchmark_data.dat` yang sama. Script kedua (5 skenario) akan menimpa hasil script pertama (14 skenario). Untuk reproducibility, beri nama berbeda dan simpan output mentah setiap run ke CSV — bukan hanya agregat.

### 8. Masih belum ada: cooldown, randomisasi urutan, std dev

14 skenario × 8 run berturut-turut tanpa jeda, urutan tetap. Dan meski Anda sudah mengumpulkan min/max, std dev tidak pernah dihitung. Simpan seluruh 8 nilai per skenario ke file, lalu hitung mean/std dari data lengkap.
