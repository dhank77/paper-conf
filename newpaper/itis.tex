\begin{abstract}
Convolutional Neural Network (CNN) super-resolution models such as FSRCNN suffer from a severe computational bottleneck in their final deconvolution layer, where naive multi-threaded CPU accumulation causes data races and non-reproducible output corruption. We propose a GPU Spatial Reduction strategy that offloads FSRCNN's Layer~8 deconvolution to isolated per-channel CUDA kernels followed by a parallel reduction pass, eliminating races by construction, and evaluate it on two architecturally distinct platforms: the NVIDIA GB10 Grace Blackwell Superchip (unified memory over NVLink-C2C) and a discrete-GPU desktop (Intel i9-14900K with an NVIDIA RTX 4090 over PCIe). Across 7-run statistical repetitions, GPU output is verified byte-for-byte identical to a race-free CPU baseline on both platforms, achieving $\text{PSNR}=\infty$/$\text{SSIM}=1.0$ against ground truth for both V1 and V2 at every configuration tested. The warp-aligned $32{\times}8$ CUDA grid is fastest at the kernel level on both GPU architectures. Against each platform's best correctness-verified CPU configuration, GPU offloading achieves $1.46\times$ (GB10, $31.5$ FPS) and up to $1.63\times$ (RTX 4090, $27$--$27.6$ FPS) speedups; a secondary, serial-baseline comparison yields $4.53\times$ on the GB10. These results establish spatial reduction as a deterministic, cross-platform-portable pattern for GPU-accelerated CNN inference.
\end{abstract}

\section{Introduction}

Edge and workstation-class AI hardware increasingly adopt SoCs where multicore CPUs and GPUs co-exist on high-speed interconnects~\cite{shi2016edge,zhou2019edge}. Super-resolution CNNs progressed from early formulations~\cite{dong2014srcnn} to FSRCNN~\cite{dong2016fsrcnn}, which achieves high quality by deferring feature extraction to low-resolution space and upscaling only at the final deconvolution layer.

That final stage (Layer~8) imposes a disproportionate computational burden: for $2\times$ upscaling ($176{\times}144 \rightarrow 352{\times}288$), it applies a $9{\times}9$ kernel across 56 channels and accumulates them into one output plane. Parallelizing this on multicore CPUs creates a dilemma: naive shared-memory accumulation causes data races and non-reproducible pixel corruption~\cite{annisa2025}, while mutex/atomic synchronization causes prohibitive lock contention. The spatial reduction pattern avoids both by writing to private per-channel buffers and reducing them in a separate deterministic pass. That said, 56 private high-resolution buffers incur real memory overhead on CPU.

We offload this deconvolution and spatial reduction to CUDA kernels on an NVIDIA GPU while parallelizing Layers 1--7 across CPU cores, achieving high throughput, memory isolation, and deterministic bit-exactness. Our contributions:
\begin{enumerate}
    \item GPU Cost-Profile Shift: privatization-reduction is a classical pattern, not a new algorithm; we show moving it to the GPU changes its cost profile qualitatively: the 43.3~MiB private buffer, expensive on CPU memory, becomes cheap in VRAM, while staying bit-exact with the CPU implementation.
    \item Warp-Aligned Grid Configuration: a $32{\times}8$ thread block maximizes memory coalescing for the deconvolution's row-major access, cutting Layer~8 kernel time $22.8\%$ (GB10) and $17.7\%$ (RTX 4090).
    \item Rigorous Statistical Evaluation: 7-run repetitions on the GB10 show GPU output byte-for-byte identical to the CPU baseline ($\text{diff\_bytes}=0$), with a $1.46\times$ speedup over the best deterministic 20-thread CPU configuration.
    \item Cross-Platform Validation: an independent replication on discrete-PCIe hardware (Intel i9-14900K + RTX 4090) confirms bit-exactness and warp-alignment generalize beyond the GB10, while surfacing a CPU thread-scheduling pathology on heterogeneous P/E-core silicon (Section~\ref{sec:rtx4090}).
\end{enumerate}

\section{Background and Baseline Architecture}

\subsection{Related Work}
CNN super-resolution progressed from early formulations~\cite{dong2014srcnn} to FSRCNN~\cite{dong2016fsrcnn}, increasingly deployed on heterogeneous CPU+GPU SoCs~\cite{shi2016edge,zhou2019edge}. Closest to ours, Annisa et al.~\cite{annisa2025} address FSRCNN Layer~8's data-race dilemma entirely on the CPU via the privatize-then-reduce pattern we adopt as V1; our contribution is orthogonal: moving that pattern to the GPU changes its cost profile qualitatively while staying bit-exact with the CPU reference. CNN inference on ARM big.LITTLE clusters scales well under proper scheduling~\cite{wang2020pipeit}, supporting our GB10 CPU baseline as non-trivial (Section~\ref{sec:gb10-speedup}). General-purpose libraries like cuDNN~\cite{chetlur2014cudnn} target convolution broadly but not this specific race-free layout (Section~III-B); we do not claim to outperform them, only to control the memory layout. Discrete-GPU PCIe transfer overhead is well documented~\cite{go2017apunet}, motivating our unified-vs-discrete memory comparison (Section~\ref{sec:rtx4090}); recent work characterizes unified physical memory for CPU-GPU accelerators directly~\cite{wahlgren2025upm}. Our RTX 4090 thread-scheduling collapse (Section~\ref{sec:rtx4090}) relates to prior work on asymmetric-CPU scheduling~\cite{bilbao2023pmcsched,eichenberger2012ompaffinity}; our contribution is an empirical observation, not a new mechanism.

\subsection{FSRCNN Architecture}
FSRCNN consists of eight layers: Feature Extraction (Layer 1), Shrinking (Layer 2), four Mapping layers (Layers 3--6), Expanding (Layer 7), and Deconvolution (Layer 8). For an input sequence at $176{\times}144$ scaled by $2\times$, Layers 1--7 operate in low-resolution ($176{\times}144$) space, outputting 56 feature maps. Layer~8 receives these 56 channels, applies a $9{\times}9$ transposed convolution~\cite{dumoulin2016convolution} with stride 2, and reduces them into a $352{\times}288$ YUV luminance output frame.

\subsection{Baseline Variants}
We analyze three distinct algorithmic variants:
\begin{itemize}
    \item V0 (Naive OpenMP CPU): Implemented in \texttt{fsrcnn\_parallel.c}. Layer~8 worker threads accumulate deconvolution outputs directly into a shared single output buffer \texttt{img\_fltr\_8}. When executed with $\text{threads} > 1$, overlapping kernel footprints cause unsynchronized read-modify-write data races, leading to output corruption, the class of bug that dynamic race detectors such as ThreadSanitizer~\cite{serebryany2009threadsanitizer} are designed to catch.
    \item V1 (Spatial Reduction CPU): Implemented in \texttt{fsrcnn\_parallel\_spatial\_reduction.c}. Eliminates data races by allocating a private intermediate buffer $\text{all\_tmp}[56 \times 352 \times 288 \times 8\,\text{B}]$ ($43.3$~MiB). Each channel writes to its own isolated offset, and a final sequential reduction pass sums the 56 channels per pixel deterministically.
    \item V2 (GPU Spatial Reduction - Proposed): Implemented in \texttt{fsrcnn\_gpu\_main.cu} and \texttt{fsrcnn\_gpu.cu}. Layers 1--7 are parallelized across CPU cores using OpenMP, while Layer~8 deconvolution and channel reduction are offloaded to CUDA kernels on the NVIDIA Blackwell GPU.
\end{itemize}

\subsection{CUDA Kernel Design and Warp Alignment}
We implement Layer~8 as two specialized hand-written CUDA kernels rather than using a general-purpose library such as cuDNN~\cite{chetlur2014cudnn}. We do not claim this is faster than a cuDNN-based deconvolution (untested, and a well-tuned library kernel could plausibly win); we only claim that it gives direct control over the private-buffer-plus-reduction layout central to our correctness argument. A head-to-head comparison against cuDNN and simpler alternatives (\texttt{atomicAdd}, output-stationary gather) is future work (Section~\ref{sec:limitations}); our result shows this design is faster and race-free relative to the CPU baseline, not that it is the fastest possible GPU design.

\subsubsection{Deconvolution Kernel (\texttt{deconv\_kernel})}
Each CUDA thread block processes a 2D tile of the input feature map. For each channel $c \in [0, 55]$, threads compute the $9{\times}9$ transposed convolution and store the result directly into an isolated channel plane inside GPU VRAM buffer \texttt{d\_all\_tmp}, indexed as $\text{index}(c, y, x) = c \times (H_{out} \times W_{out}) + y \times W_{out} + x$.

\subsubsection{Spatial Reduction Kernel (\texttt{spatial\_reduction\_kernel})}
After deconvolution completes, the spatial reduction kernel assigns one CUDA thread per high-resolution output pixel $(y, x)$. The thread iterates across all 56 channel planes in \texttt{d\_all\_tmp}, sums the values, and adds the Layer~8 bias:
\begin{equation}
\text{output}[y, x] = \left( \sum_{c=0}^{55} \text{d\_all\_tmp}[c, y, x] \right) + \text{bias}_8
\end{equation}

Because channel writes are fully isolated during deconvolution and read-only during reduction, the execution is completely race-free and deterministic.

NVIDIA GPUs execute threads in SIMD groups of 32 called \emph{warps}~\cite{nvidiacudaguide}. Standard $16{\times}16$ blocks place only 16 threads along the row-major X dimension, causing consecutive warps to straddle non-contiguous memory rows. Since warp/block sizing has a first-order effect on SIMT throughput~\cite{lashgar2012warpresize}, we evaluate a $32{\times}8$ block (256 threads): setting $B_x=32$ guarantees all 32 threads in a warp access contiguous doubles along one image row, maximizing coalescing.

\section{Experimental Evaluation}

\subsection{Evaluation Methodology}
\label{sec:methodology}
Experiments were conducted on the ASUS Ascent GX10 under Ubuntu 24.04 LTS ARM64. The workload consists of 150 frames of the Suzie video sequence ($176{\times}144 \rightarrow 352{\times}288$, YUV420p).

To guarantee statistical rigor, every configuration was executed for 7 repetitions: run 1 discarded as cold-start/warmup, runs 2--7 (6 runs) recorded as Mean $\pm$ SD.

\emph{Reproducibility:} CPU binaries are compiled with \texttt{gcc -fopenmp -O3} (no \texttt{-march=native}/\texttt{-ffast-math}); parallel loops use plain \texttt{\#pragma omp parallel for} with no explicit \texttt{schedule()}, so thread placement follows the OpenMP runtime's default (GNU \texttt{libgomp}: static). The GPU binary is compiled with \texttt{nvcc -O3 -std=c++11 -arch=native} (\texttt{sm\_121} on GB10, \texttt{sm\_89} on RTX 4090). CUDA Toolkit 13.0 was used on both platforms (Table~\ref{tab:hardware}); exact GCC/NVCC point releases were not logged.

Correctness was assessed two ways: a direct byte comparison (\texttt{cmp -l}) between V1 and V2 output ($\text{diff\_bytes}=0$ across all grid configurations), and scoring against \texttt{ground\_truth.yuv} via byte diff, PSNR, and SSIM~\cite{wang2004ssim} (\texttt{ffmpeg}). V1 and V2 are bit-exact against ground truth at every configuration tested, on both platforms ($\text{PSNR}=\infty$, $\text{SSIM}=1.0$; Tables~\ref{tab:benchmark}, \ref{tab:rtx-benchmark}). V0, in contrast, shows real, non-monotonic degradation from its data race, dropping as low as $13.8$~dB/$0.518$ (GB10, 4 threads) and $23.0$~dB/$0.845$ (RTX 4090, 32 threads). Fig.~\ref{fig:correctness} shows this directly (ground truth, V1, V2 visually identical; V0 shows clear scanline corruption from unsynchronized writes to \texttt{img\_fltr\_8}). On both platforms V0 is bit-exact only while genuinely single-threaded, then drops sharply once concurrent writes begin, with no consistent recovery as thread count rises further (Tables~\ref{tab:benchmark}, \ref{tab:rtx-benchmark}).

\section{Discussion and Key Insights}

\subsection{Speedup vs. Maxed-Out CPU Cores, and Warp Alignment}
\label{sec:gb10-speedup}
We report GPU speedup against CPU V1, not V0, throughout: V1 is race-free by construction at every thread count, while V0 is only \emph{incidentally} correct at 1 thread (no concurrency to race on) and degrades with more threads (Table~\ref{tab:benchmark}). V0 is in fact the raw-wall-time winner at 20 threads ($6{,}308.83$~ms, faster than V1 and giving only $1.34\times$ GPU speedup if used), but we exclude it as a baseline since its output there is not verified correct; we state the number here rather than omitting it.

GPU V2 ($32{\times}8\_256$) reaches $4{,}756.33$~ms end-to-end ($31.5$ FPS). Against CPU V1's 20-thread configuration ($6{,}921.83$~ms, the fastest correctness-verified CPU result) this is $1.46\times$ ($46\%$ faster), our primary headline figure, consistent with how we report the RTX 4090 (Section~\ref{sec:rtx4090}). Against V1's serial time ($21{,}552.33$~ms) the figure is a larger, secondary $4.53\times$; using V0's slightly faster serial time ($18{,}240.50$~ms, numerically identical output at 1 thread) instead would inflate this by $\sim$18\% ($3.84\times$ vs. $4.53\times$), so we use V1 throughout for consistency with the primary comparison.

This $1.46\times$ is notable given CNN inference scales well on ARM big.LITTLE clusters when properly scheduled~\cite{wang2020pipeit}; the GB10 CPU baseline is not a strawman. GPU V2 also has lower variance ($\pm30.71$~ms) than any CPU V1 configuration (e.g. $\pm998.43$~ms at 8 threads). Figure~\ref{fig:thread-scaling}(a) plots both CPU variants across the full thread ladder: unlike the RTX 4090 (Fig.~\ref{fig:thread-scaling}(b)), the GB10's 20 homogeneous cores (no SMT) scale smoothly with no collapse.

Shifting from the default $16{\times}16$ grid ($701.51$~ms kernel time) to the warp-aligned $32{\times}8$ grid ($541.59$~ms) reduces Layer~8 kernel time by $159.92$~ms ($22.8\%$). We attribute this to memory coalescing: a 32-thread-wide block lets every thread in a warp issue a request into the same coalesced transaction, rather than splitting it across multiple transactions as a 16-wide block does. This is consistent with the timing but not directly profiled (e.g. via \texttt{ncu} load-efficiency counters); we list that verification as future work (Section~\ref{sec:limitations}).

\subsection{NVLink-C2C Transfer Asymmetry and Amdahl's Law}
\label{sec:nvlink}
Device-to-Host transfer required only $3.61$~ms total ($0.024$~ms/frame): returning results over NVLink-C2C is effectively free. Host-to-Device transfer of the Layer~1--7 feature maps, however, measured $516.74$~ms ($3.44$~ms/frame, $10.9\%$ of wall time), two orders of magnitude larger despite sharing the same interconnect. This asymmetry is more consistent with host-side staging/synchronization overhead (e.g. non-pinned memory, or a blocking copy before the GPU stream is ready) than with raw bandwidth limits, and is a concrete optimization target (e.g. pinned/managed buffers) rather than an NVLink-C2C bottleneck.

Per Table~\ref{tab:breakdown}, offloading Layer~8 reduced its kernel time to $531.08$~ms ($3.54$~ms/frame), leaving CPU Layers 1--7 at $71.5\%$ of wall time (H2D a further $10.9\%$): the serial-fraction bottleneck that Amdahl's Law~\cite{amdahl1967} predicts once the parallel stage is optimized away. Offloading Layers 1--7 to Tensor Cores, combined with resolving the H2D asymmetry above, is the clearest path to sub-second reconstruction; a Roofline analysis~\cite{williams2009roofline} would clarify whether that offload is compute- or memory-bound first.

\section{Cross-Platform Validation on Discrete-GPU Hardware}
\label{sec:rtx4090}

To test whether the GPU Spatial Reduction approach generalizes beyond the GB10's unified-memory architecture, we replicated the experiment on a conventional discrete-GPU desktop (Intel Core i9-14900K + NVIDIA RTX 4090; specifications in Table~\ref{tab:hardware}), where CPU (system DDR) and GPU (VRAM) memory are physically separate and connected over PCIe rather than NVLink-C2C. Unlike the GB10's 20 homogeneous-per-tier ARM cores with no simultaneous multithreading (SMT), this CPU has a heterogeneous 8~Performance-core~+~16~Efficiency-core layout where only the P-cores support Hyper-Threading, yielding 24 physical / 32 logical threads.

\subsection{Platform-Specific Methodology Adjustment}
A first attempt reusing the GB10's thread ladder (1--20) and fixed 20-thread CPU backdrop produced misleading results here: wall time collapsed past 8 threads ($\sim$3.5$\times$ slower than the 4-thread optimum), and since that degraded configuration backdropped every GPU grid-search run, results were dominated by CPU contention rather than the GPU kernel. We therefore (1) swept a topology-correct ladder (1, 2, 4, 8, 16, 24, 32, matching this chip's core boundaries) and (2) used this platform's own best CPU configuration (4 threads) as the backdrop, rather than assuming more threads is optimal. \subsection{The Collapse Is Reproducible, and GPU Speedup Against a Fair Baseline}
The collapse was observed independently across \emph{three} separate full runs (two on the 1--20 ladder, one on the corrected 1--32 ladder reported here), with tight SDs at each collapsed point (e.g. 16 threads: $29{,}341\pm240$~ms here vs. $29{,}511\pm125$ and $29{,}609\pm249$~ms previously), which rules out a one-off artifact. This chip's P/E-core split relies on Intel Thread Director for scheduling, and asymmetric-CPU system software generally needs explicit heterogeneity awareness to avoid throughput loss~\cite{bilbao2023pmcsched}; the generic OpenMP pool used here has no such affinity control~\cite{eichenberger2012ompaffinity} (\texttt{OMP\_PLACES}/\texttt{proc\_bind}), so past 8 threads the scheduler appears to actively hurt throughput. Peak performance is at exactly 4 threads, not the nominal 32-thread maximum. This optimum does not cleanly match the chip's topology (8 P-cores, Table~\ref{tab:hardware}), so we do not claim a confirmed topological explanation, and cannot rule out memory-bandwidth or DVFS/thermal effects without a control experiment (Section~\ref{sec:limitations}). Figure~\ref{fig:thread-scaling}(b) plots this curve.

With the CPU backdrop corrected, GPU V2 reaches $5{,}435$--$5{,}579$~ms end-to-end ($26.9$--$27.6$ FPS), a $1.59\times$--$1.63\times$ speedup over CPU V1's best configuration (4 threads, $8{,}844.17$~ms), not the inflated $4\times$+ figure from comparing against V1's serial time or the degraded 32-thread configuration. Using the same ``best deterministic CPU'' standard on both platforms (Section~\ref{sec:gb10-speedup}), this is somewhat larger than the GB10's $1.46\times$, consistent with V1's parallel scaling here being more constrained by the thread-scheduling collapse than the GB10's CPU is.

\subsection{Warp Alignment Generalizes Across GPU Architectures}
At the kernel level, $32{\times}8$ remains fastest on this Ada Lovelace GPU ($358.14$~ms), $17.7\%$ faster than $16{\times}16$ ($435.17$~ms) and $18.7\%$ faster than the slowest configuration ($440.70$~ms), confirming the warp-aligned coalescing argument from Section~III-B (a consequence of CUDA's 32-thread warp granularity~\cite{nvidiacudaguide}) is a property of CUDA itself, not specific to the GB10. At the \emph{wall-clock} level the five configurations remain statistically hard to distinguish ($5{,}435$--$5{,}579\pm101$--$222$~ms, overlapping error bars) even though $32{\times}8$ nominally wins both metrics here; the kernel-level advantage is only cleanly visible via CUDA-event profiling, reinforcing why Section~\ref{sec:methodology}'s instrumentation matters. \subsection{Non-Unified Memory and FP64 Precision}
This platform's CPU/GPU memory is physically separate (63~GB DDR vs. 24~GB GDDR6X over PCIe), unlike the GB10's unified LPDDR5x pool over NVLink-C2C~\cite{nvidiagracehopper2022}, a distinction that recent work on unified physical memory for accelerators is beginning to study directly~\cite{wahlgren2025upm}. Despite this, GPU V2's Layer~8 kernel ($358.14$~ms) is faster in absolute terms than the GB10's ($541.59$~ms), likely reflecting the RTX 4090's raw compute advantage outweighing PCIe cost for a payload this small ($\approx$44~MiB); discrete-GPU PCIe/DMA overhead is well documented for more transfer-bound workloads~\cite{go2017apunet}, so its absence here is plausibly payload-size-dependent. We did not capture a separate H2D/D2H breakdown here (Section~\ref{sec:limitations}), so we cannot yet confirm this bottleneck is genuinely absent rather than just small relative to this GPU's compute advantage.

All V1/V2 arithmetic uses double precision (\texttt{double}), matching the CPU baseline and making the bit-exact CPU$\equiv$GPU comparison (Section~\ref{sec:methodology}) as strict as possible; FP32 would admit more CPU/GPU rounding divergence even for a logically-equivalent computation. This has a real cost on the RTX 4090: as a consumer GPU, its FP64 throughput is architecturally $1/64$ of its FP32 throughput ($\approx 1.3$ vs. $\approx 82.6$ TFLOPS), so the $358.14$~ms optimal kernel time (Section~\ref{sec:rtx4090}) is achieved with its dominant compute resource largely idle; an FP32 implementation would plausibly be substantially faster, at the cost of weakening bit-exactness to a numerical-tolerance claim. The GB10's datacenter-class GPU has a much smaller FP64:FP32 gap, so this trade-off is less severe there (not separately quantified). See Section~\ref{sec:limitations} for the FP32 ablation this motivates.

\section{Limitations and Future Work}
\label{sec:limitations}
Ordered roughly by priority:
\begin{itemize}
    \item No competitive GPU baseline: V2 is compared only against CPU implementations, not alternatives (\texttt{atomicAdd} accumulation, an output-stationary gather kernel, or cuDNN, Section~III-B), the highest-priority follow-up.
    \item FP64 throughout, unquantified FP32 trade-off: no FP32 ablation was run to quantify the speedup vs. bit-exactness trade-off discussed in Section~\ref{sec:rtx4090}.
    \item Warp-alignment mechanism not directly profiled: the coalescing explanation (Section~III-B) is consistent with timing but unverified by profiler counters (e.g. \texttt{ncu}); a sweep including non-aligned widths (e.g. $64{\times}4$) would help isolate the effect.
    \item RTX 4090 collapse not isolated from confounds: no \texttt{OMP\_PROC\_BIND}/\texttt{OMP\_PLACES} control experiment was run, so memory-bandwidth saturation, DVFS/thermal throttling, or false sharing remain possible alongside scheduler oversubscription.
    \item No H2D/D2H breakdown on the RTX 4090: unlike the GB10 (Table~\ref{tab:breakdown}), transfer overhead was not isolated there, the central unified-vs-discrete comparison this paper's title promises.
    \item Per-run variance not captured: PSNR/SSIM and GPU kernel times are single measurements per configuration, not 6-run means, weakening (not invalidating) associated percentage claims.
    \item Single test sequence/resolution: all results use the 150-frame QCIF-to-CIF Suzie sequence; higher resolutions (e.g. 1080p) would shift the compute-to-transfer ratio.
\end{itemize}

\section{Conclusion}

In this paper, we introduced a GPU Spatial Reduction framework for accelerating FSRCNN's Layer~8 deconvolution, evaluated on two architecturally distinct platforms. On both, V1 (CPU) and V2 (GPU spatial reduction) are bit-exact against ground truth at every configuration tested ($\text{PSNR}=\infty$, $\text{SSIM}=1.0$), while V0's naive accumulation shows real, non-monotonic data-race corruption (as low as $13.8$~dB/$0.518$ SSIM on the GB10; Fig.~\ref{fig:correctness}). On the GB10, the optimal $32{\times}8$ grid achieves $1.46\times$ speedup ($31.5$ FPS) over CPU V1's best correctness-verified configuration ($4.53\times$ vs. serial, reported only as a secondary figure, Section~\ref{sec:gb10-speedup}); the GPU Layer~8 kernel completes in $541.59$~ms while also surfacing a $516.74$~ms host-to-device transfer asymmetry (Section~\ref{sec:nvlink}). Cross-platform validation on a discrete-GPU desktop (Intel i9-14900K + RTX 4090, Section~\ref{sec:rtx4090}) confirms $32{\times}8$ remains fastest at the kernel level on a second GPU architecture, with GPU V2 outperforming that platform's best CPU configuration by up to $1.63\times$ despite non-unified memory, while also surfacing a CPU thread-scheduling pathology independent of our GPU contribution. Section~\ref{sec:limitations} lists the follow-up experiments needed to fully close out these findings.
