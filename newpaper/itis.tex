\begin{abstract}
Convolutional Neural Network (CNN) super-resolution models such as FSRCNN suffer from a severe computational bottleneck in their final deconvolution layer, where naive multi-threaded CPU accumulation causes data races and non-reproducible output corruption. We propose a GPU Spatial Reduction strategy that offloads FSRCNN's Layer~8 deconvolution to isolated per-channel CUDA kernels followed by a parallel reduction pass, eliminating races by construction, and evaluate it on two architecturally distinct platforms: the NVIDIA GB10 Grace Blackwell Superchip (unified memory over NVLink-C2C) and a discrete-GPU desktop (Intel i9-14900K with an NVIDIA RTX 4090 over PCIe). Across 7-run statistical repetitions, GPU output is verified byte-for-byte identical to a race-free CPU baseline on both platforms, achieving $\text{PSNR}=\infty$/$\text{SSIM}=1.0$ against ground truth for both V1 and V2 at every configuration tested. The warp-aligned $32{\times}8$ CUDA grid is fastest at the kernel level on both GPU architectures. Against each platform's best correctness-verified CPU configuration, GPU offloading achieves $1.46\times$ (GB10, $31.5$ FPS) and up to $1.63\times$ (RTX 4090, $27$--$27.6$ FPS) speedups; a secondary, serial-baseline comparison yields $4.53\times$ on the GB10. These results establish spatial reduction as a deterministic, cross-platform-portable pattern for GPU-accelerated CNN inference.
\end{abstract}

\section{Introduction}

Edge computing and workstation-class AI hardware have increasingly adopted unified architecture SoCs where high-performance multicore CPUs and graphics accelerators co-exist on high-speed interconnects~\cite{shi2016edge,zhou2019edge}. Super-resolution algorithms have progressed from early CNN formulations~\cite{dong2014srcnn} to the Fast Super-Resolution Convolutional Neural Network (FSRCNN)~\cite{dong2016fsrcnn}, which are widely deployed in video processing pipelines for real-time video reconstruction. FSRCNN achieves high quality by deferring feature extraction and non-linear mapping to low-resolution space and performing feature upscaling only at the final stage via a deconvolution layer.

However, the final deconvolution stage (Layer~8 in FSRCNN) imposes a disproportionately heavy computational burden. In a typical $2\times$ upscaling scenario ($176{\times}144 \rightarrow 352{\times}288$), Layer~8 applies a $9{\times}9$ kernel across 56 feature channels and accumulates their contributions into a single high-resolution output plane. On multicore CPUs, parallelizing this channel reduction leads to a critical dilemma: naive multi-threading with shared memory accumulation introduces severe data races and non-reproducible pixel corruption~\cite{annisa2025}, while mutex-based or atomic synchronization introduces prohibitive lock contention.

To eliminate both memory contention and data races, the spatial reduction pattern allocates private per-channel output buffers ($all\_tmp$) and reduces them in a separate deterministic pass. While effective on CPUs, allocating 56 private high-resolution channel buffers on CPU memory incurs noticeable memory consumption and scaling overhead on asymmetric multicore processors.

In this work, we present a GPU Spatial Reduction Architecture designed for modern unified memory AI supercomputers. By offloading the 56-channel deconvolution and spatial reduction of Layer~8 to CUDA kernels on an NVIDIA Blackwell GPU while parallelizing Layers 1--7 across ARM CPU cores, we achieve high throughput, strict memory isolation, and deterministic bit-exactness.

Our primary contributions are:
\begin{enumerate}
    \item GPU Cost-Profile Shift for Privatization-Reduction: The privatization-plus-reduction pattern behind V1 is a classical technique for parallel array reductions, not a new algorithmic design in itself; our contribution is showing that moving this pattern to the GPU qualitatively changes its cost profile — the 43.3~MiB private-buffer allocation that is comparatively expensive on CPU memory becomes cheap in GPU VRAM, while bit-exact determinism relative to the CPU implementation is preserved (Section~\ref{sec:methodology}).
    \item Warp-Aligned Grid Configuration: A grid configuration comparison demonstrating that a $32{\times}8$ thread block layout maximizes memory coalescing for the 9$\times$9 deconvolution's row-major access pattern, reducing Layer~8 kernel execution time by $22.8\%$ compared to a standard $16{\times}16$ layout on the GB10, and by $17.7\%$ on a second, independently-tested GPU (NVIDIA RTX 4090).
    \item Rigorous Statistical Evaluation with Verified Bit-Exact Equivalence: Benchmark results over 7-run statistical repetitions (Mean $\pm$ SD) on the ASUS Ascent GX10 (NVIDIA GB10 Grace Blackwell Superchip), demonstrating that GPU output V2 is byte-for-byte identical to the deterministic CPU spatial-reduction baseline V1 ($\text{diff\_bytes}=0$), while achieving a $1.46\times$ speedup over the platform's best deterministic 20-thread CPU configuration.
    \item Cross-Platform Validation on Discrete-GPU Hardware: An independent replication on an architecturally distinct platform (Intel i9-14900K + NVIDIA RTX 4090, discrete PCIe-attached memory rather than the GB10's unified NVLink-C2C pool) confirming bit-exact equivalence and warp-alignment behavior generalize beyond the GB10, while also surfacing a CPU thread-scheduling pathology on heterogeneous P-core/E-core silicon that is a confound for any CPU baseline on such hardware (Section~\ref{sec:rtx4090}).
\end{enumerate}

\section{Background and Baseline Architecture}

\subsection{Related Work}
CNN-based super-resolution has progressed from early formulations~\cite{dong2014srcnn} to FSRCNN's low-resolution-space feature extraction~\cite{dong2016fsrcnn}, and deployment increasingly targets edge and workstation-class heterogeneous SoCs where CPU and GPU (or big.LITTLE CPU clusters) share a chip or package~\cite{shi2016edge,zhou2019edge}. The closest prior work to ours is Annisa and Adnan~\cite{annisa2025}, who identify the same Layer~8 data-race dilemma on AMP (asymmetric multicore processor) architectures and address it entirely on the CPU side via the spatial-reduction (privatize-then-reduce) pattern that we adopt as our V1 baseline; our contribution is orthogonal — rather than restructuring the reduction on CPU, we move it to the GPU and show the same pattern's cost profile changes qualitatively when the private buffer lives in VRAM instead of system RAM, while remaining bit-exact with the CPU reference. Separately, CNN inference throughput on heterogeneous ARM big.LITTLE CPU clusters has been shown to scale favorably under scheduling-aware designs~\cite{wang2020pipeit}, which we use as context for treating our GB10 CPU baseline as a reasonably strong comparator rather than a strawman (Section~\ref{sec:gb10-speedup}).

On the systems side, general-purpose deep learning primitive libraries such as cuDNN~\cite{chetlur2014cudnn} provide optimized convolution/deconvolution kernels but do not target the specific race-free privatization-reduction layout central to this paper (Section~III-B); we do not claim performance superiority over such libraries, only implementation control (Section~III-B). Discrete-GPU systems connected over PCIe are well known to incur DMA/transfer overhead for transfer-bound workloads~\cite{go2017apunet}, motivating our platform comparison between the GB10's unified NVLink-C2C memory pool and the RTX 4090's discrete PCIe-attached VRAM (Section~\ref{sec:rtx4090}); recent systems work is beginning to characterize unified physical memory for CPU-GPU accelerators directly~\cite{wahlgren2025upm}, a direction complementary to our empirical cross-platform comparison. Finally, our RTX 4090 thread-scheduling collapse (Section~\ref{sec:rtx4090}) sits alongside a body of work on scheduling for asymmetric/heterogeneous multicore CPUs, including Intel's own hybrid-architecture guidance~\cite{intelhybrid2021}, system-software schedulers for Alder-Lake-class asymmetric cores~\cite{bilbao2023pmcsched}, and OpenMP's thread affinity model~\cite{eichenberger2012ompaffinity} — our contribution here is an empirical observation (a specific, reproducible collapse on real hardware) rather than a new scheduling mechanism.

\subsection{FSRCNN Architecture}
FSRCNN consists of eight layers: Feature Extraction (Layer 1), Shrinking (Layer 2), four Mapping layers (Layers 3--6), Expanding (Layer 7), and Deconvolution (Layer 8). For an input sequence at $176{\times}144$ scaled by $2\times$, Layers 1--7 operate in low-resolution ($176{\times}144$) space, outputting 56 feature maps. Layer~8 receives these 56 channels, applies a $9{\times}9$ transposed convolution~\cite{dumoulin2016convolution} with stride 2, and reduces them into a $352{\times}288$ YUV luminance output frame.

\subsection{Baseline Variants}
We analyze three distinct algorithmic variants:
\begin{itemize}
    \item V0 (Naive OpenMP CPU): Implemented in \texttt{fsrcnn\_parallel.c}. Layer~8 worker threads accumulate deconvolution outputs directly into a shared single output buffer \texttt{img\_fltr\_8}. When executed with $\text{threads} > 1$, overlapping kernel footprints cause unsynchronized read-modify-write data races, leading to output corruption — the class of bug dynamic race detectors such as ThreadSanitizer~\cite{serebryany2009threadsanitizer} are designed to catch.
    \item V1 (Spatial Reduction CPU): Implemented in \texttt{fsrcnn\_parallel\_spatial\_reduction.c}. Eliminates data races by allocating a private intermediate buffer $\text{all\_tmp}[56 \times 352 \times 288 \times 8\,\text{B}]$ ($43.3$~MiB). Each channel writes to its own isolated offset, and a final sequential reduction pass sums the 56 channels per pixel deterministically.
    \item V2 (GPU Spatial Reduction - Proposed): Implemented in \texttt{fsrcnn\_gpu\_main.cu} and \texttt{fsrcnn\_gpu.cu}. Layers 1--7 are parallelized across CPU cores using OpenMP, while Layer~8 deconvolution and channel reduction are offloaded to CUDA kernels on the NVIDIA Blackwell GPU.
\end{itemize}

\subsection{CUDA Kernel Design}
We implement Layer~8 as two specialized hand-written CUDA kernels, rather than using a general-purpose deep learning primitive library such as cuDNN~\cite{chetlur2014cudnn}. We do not claim this hand-written approach is faster than a cuDNN-based deconvolution — we have not benchmarked one against the other, and a well-tuned library kernel could plausibly outperform our implementation — only that it gives us direct control over the private-buffer-plus-reduction memory layout central to this paper's correctness argument. A head-to-head comparison against cuDNN (and against simpler alternatives such as a single \texttt{atomicAdd}-based kernel or an output-stationary gather formulation that avoids the intermediate buffer entirely) is listed as future work in Section~\ref{sec:limitations}; without it, our result establishes that this particular GPU design is faster and race-free relative to the CPU baseline, not that it is the fastest possible race-free GPU design.

\subsubsection{Deconvolution Kernel (\texttt{deconv\_kernel})}
Each CUDA thread block processes a 2D tile of the input feature map. For each channel $c \in [0, 55]$, threads compute the $9{\times}9$ transposed convolution and store the result directly into an isolated channel plane inside GPU VRAM buffer \texttt{d\_all\_tmp}, indexed as $\text{index}(c, y, x) = c \times (H_{out} \times W_{out}) + y \times W_{out} + x$.

\subsubsection{Spatial Reduction Kernel (\texttt{spatial\_reduction\_kernel})}
After deconvolution completes, the spatial reduction kernel assigns one CUDA thread per high-resolution output pixel $(y, x)$. The thread iterates across all 56 channel planes in \texttt{d\_all\_tmp}, sums the values, and adds the Layer~8 bias:
\begin{equation}
\text{output}[y, x] = \left( \sum_{c=0}^{55} \text{d\_all\_tmp}[c, y, x] \right) + \text{bias}_8
\end{equation}

Because channel writes are fully isolated during deconvolution and read-only during reduction, the execution is completely race-free and deterministic.

\subsection{Warp Alignment Optimization ($32{\times}8$ Block Grid)}
NVIDIA GPUs execute threads in SIMD groups of 32 called \emph{warps}~\cite{nvidiacudaguide}. Standard 2D thread block configurations such as $16{\times}16$ (256 threads) place 16 threads along the X (horizontal) dimension. In a row-major image layout, this causes consecutive warps to straddle non-contiguous memory rows.

Consistent with prior findings that warp/thread-block sizing has a first-order effect on SIMT throughput~\cite{lashgar2012warpresize}, we parameterize thread block dimensions $(B_x, B_y)$ and evaluate a $32{\times}8$ block layout (32 threads wide by 8 threads high, total 256 threads). Setting $B_x = 32$ guarantees that all 32 threads within a warp access contiguous 64-bit double-precision values along a single image row in LPDDR5x VRAM, maximizing memory coalescing and instruction throughput.

\section{Experimental Evaluation}

\subsection{Evaluation Methodology}
\label{sec:methodology}
Experiments were conducted on the ASUS Ascent GX10 under Ubuntu 24.04 LTS ARM64. The workload consists of 150 frames of the Suzie video sequence ($176{\times}144 \rightarrow 352{\times}288$, YUV420p).

To guarantee statistical rigor, every test configuration was executed for 7 repetitions:
\begin{itemize}
    \item Run 1: Discarded as a cold-start / warmup run.
    \item Runs 2--7 (6 runs): Recorded to calculate Mean and Sample Standard Deviation ($\text{Mean} \pm \text{SD}$).
\end{itemize}

Output correctness was assessed two ways. First, we performed a direct byte-level comparison (\texttt{cmp -l}) between the CPU spatial-reduction output (V1) and the GPU spatial-reduction output (V2); across all tested grid configurations, $\text{diff\_bytes}=0$, i.e. V2 is bit-exact with V1. Second, every variant's output was scored against \texttt{ground\_truth.yuv} (generated by the single-threaded V1 procedure in Section~IV-B) using byte-level diff, PSNR, and the Structural Similarity Index Measure (SSIM)~\cite{wang2004ssim} (via \texttt{ffmpeg}). V1 and V2 are bit-exact against ground truth at every thread count and every grid configuration tested, on both the GB10 and the RTX 4090 ($\text{diff\_bytes}=0$, $\text{PSNR}=\infty$, $\text{SSIM}=1.0$ throughout; Tables~\ref{tab:benchmark}, \ref{tab:rtx-benchmark}), confirming GPU offloading introduces no numerical deviation from the deterministic CPU reference. V0, in contrast, shows real, non-monotonic PSNR/SSIM degradation from its known data race, varying by thread count and by platform — as low as $13.8$~dB/$0.518$ SSIM (GB10, 4 threads) and $23.0$~dB/$0.845$ SSIM (RTX 4090, 32 threads) — consistent with race severity depending on scheduling/contention timing rather than thread count alone. Fig.~\ref{fig:correctness} shows this directly: ground truth, V1, and V2 are visually and numerically identical, while V0 (32 threads) shows clear horizontal-scanline corruption from unsynchronized concurrent writes to \texttt{img\_fltr\_8} — direct visual and numerical confirmation of the data-race motivation stated in Section~I. Figure~\ref{fig:v0-severity} plots V0's PSNR against thread count on both platforms, showing this non-monotonicity is not a one-off: PSNR dips sharply once concurrency begins, partially recovers, then never returns to bit-exact.

\subsection{Reproducibility}
CPU binaries (V0, V1) are compiled with \texttt{gcc -fopenmp -O3} and linked against \texttt{libm}; no \texttt{-march=native}, \texttt{-ffast-math}, or other aggressive/non-default optimization flags are used. Parallel loops use plain \texttt{\#pragma omp parallel for} with no explicit \texttt{schedule()} clause, so thread-to-iteration assignment follows the OpenMP runtime's default policy (implementation-defined; the GNU \texttt{libgomp} runtime used here defaults to static scheduling) rather than an application-tuned one. The GPU binary (V2) is compiled with \texttt{nvcc -O3 -std=c++11}, targeting the platform's native architecture (\texttt{-arch=native}, resolving to \texttt{sm\_121} on the GB10 and \texttt{sm\_89} on the RTX 4090) with \texttt{-Xcompiler -fopenmp -Xcompiler -fno-tree-vectorize} for the CPU-side Layers 1--7 portion of the hybrid pipeline. We did not pin exact GCC/NVCC point-release version numbers in our logs; CUDA Toolkit 13.0 was used on both platforms (Table~\ref{tab:hardware}, Table~\ref{tab:hardware-rtx}).

\section{Discussion and Key Insights}

\subsection{Speedup vs. Maxed-Out CPU Cores}
\label{sec:gb10-speedup}
We report GPU speedup against CPU V1's own configurations throughout, rather than V0's, for a specific reason: V1 is race-free by construction at every thread count, while V0 is only \emph{incidentally} correct at 1 thread because there is no concurrency to race on. Table~\ref{tab:benchmark} shows V0's PSNR/SSIM degrading as thread count rises (data-race corruption), so V0 is not a correctness-verified baseline at any parallel configuration, and we do not use it for speedup comparisons despite it being the raw-wall-time winner in places (V0 at 20 threads: $6{,}308.83$~ms, the fastest CPU configuration measured on this platform in absolute terms — faster than V1 at 20 threads and faster than GPU V2 would be judged against if this number were used as the denominator, giving only a $1.34\times$ GPU speedup). We consider this an invalid comparison precisely because V0's output at 20 threads is not verified correct, but we state the number explicitly here rather than omitting it.

Our proposed GPU Spatial Reduction ($32{\times}8\_256$) achieves an end-to-end wall time of $4{,}756.33$~ms for the 150-frame sequence, i.e. $31.5$ frames per second (FPS) — a concrete throughput figure for the real-time video reconstruction motivation stated in Section~I. Against CPU V1's deterministic 20-thread configuration ($6{,}921.83$~ms) — the platform's fastest \emph{correctness-verified} CPU result — this is a $1.46\times$ speedup ($46\%$ faster), which we treat as the primary, apples-to-apples headline figure, consistent with how we report the RTX 4090 platform (Section~\ref{sec:rtx4090}). Against V1's single-threaded serial time ($21{,}552.33$~ms) the speedup is a larger $4.53\times$; we report this only as a secondary, explicitly-labeled ``vs. serial'' figure, since a serial CPU baseline is a much weaker comparator than a fully parallelized one and we do not want to imply the two numbers are interchangeable. We also note that using V1's serial time rather than V0's slightly faster serial time ($18{,}240.50$~ms, which produces numerically identical output to V1 at 1 thread per Table~\ref{tab:benchmark}) as the ``vs. serial'' denominator is itself a choice that inflates this secondary figure by about $18\%$ ($4.53\times$ vs. $3.84\times$); we use V1 throughout for consistency with the primary (parallel) comparison above, not because it is the faster serial option.

Crucially, GPU V2 outperforms the 20-core CPU execution by $1.46\times$ — notable given that CNN inference workloads have been shown to scale well across ARM big.LITTLE-style heterogeneous CPU clusters when properly scheduled~\cite{wang2020pipeit}, meaning this GB10 CPU baseline is not a strawman. GPU V2 also exhibits lower variance ($\text{SD} = \pm 30.71$~ms) than every CPU V1 thread configuration measured, most notably at contended thread counts (e.g. $\text{SD} = \pm 998.43$~ms on 8 threads), consistent with GPU offloading avoiding CPU thread scheduling jitter. Figure~\ref{fig:gx10-scaling} plots both CPU variants' wall time across the full thread ladder: unlike the RTX 4090 (Section~\ref{sec:rtx4090}), the GB10's 20 homogeneous-per-tier cores with no SMT scale smoothly to their maximum, with no oversubscription collapse.

\subsection{Warp Alignment Optimization}
Comparing GPU block configurations reveals the importance of warp alignment. Shifting from the default $16{\times}16$ grid ($701.51$~ms kernel time) to the warp-aligned $32{\times}8$ grid ($541.59$~ms kernel time) reduces Layer~8 kernel execution time by $159.92$~ms ($22.8\%$ acceleration). We attribute this to memory coalescing: because a CUDA warp consists of 32 threads, a 32-thread horizontal width lets every thread in a warp issue a request into the same coalesced memory transaction, rather than splitting the warp's requests across multiple transactions as a 16-wide block does. This explanation is consistent with the measured timing difference, but we did not directly profile memory transaction efficiency (e.g. via \texttt{ncu} global load efficiency counters) to confirm coalescing is the mechanism rather than correlated with it; we list this as a concrete verification step for future work (Section~\ref{sec:limitations}).

\subsection{NVLink-C2C Transfer Asymmetry}
\label{sec:nvlink}
Device-to-Host transfer (\texttt{d2h\_ms}) for all 150 high-resolution output frames required only $3.61$~ms ($0.024$~ms/frame), confirming that returning Layer~8 results over the NVLink-C2C interconnect is effectively free. Host-to-Device transfer (\texttt{h2d\_ms}) of the 56-channel Layer~1--7 feature maps, however, measured $516.74$~ms ($3.44$~ms/frame, $10.9\%$ of wall time) — over two orders of magnitude larger than the return transfer, despite both directions sharing the same interconnect. Since payload size is comparable in both directions (56 channels in, 1 channel out, but the input side carries more raw feature data), this asymmetry is more consistent with host-side staging or synchronization overhead (e.g. non-pinned host memory, or a blocking copy issued before the GPU stream is ready) than with raw interconnect bandwidth limits. This is a concrete optimization target for follow-up work (e.g. pinned/managed memory buffers), rather than a bottleneck NVLink-C2C itself imposes.

\subsection{Amdahl's Law Pipeline Analysis}
As shown in Table~\ref{tab:breakdown}, offloading Layer~8 to GPU reduced Layer~8 kernel execution time to $531.08$~ms ($3.54$~ms/frame) in the profiled run. CPU Layers 1--7 account for $71.5\%$ of total wall time, with the H2D transfer identified above contributing a further $10.9\%$. Even after accounting for transfer overhead, CPU Layers 1--7 remain the single largest share of the pipeline — the serial-fraction bottleneck Amdahl's Law~\cite{amdahl1967} predicts once the parallelizable stage is optimized away — so future work offloading Layers 1--7 to Tensor Cores — combined with resolving the H2D asymmetry in Section~\ref{sec:nvlink} — represents the clearest path toward sub-second end-to-end video reconstruction. A Roofline-style analysis~\cite{williams2009roofline} of the remaining CPU stages would help determine whether that future offload is compute- or memory-bound before committing to a Tensor Core port.

\subsection{The Collapse Is Reproducible, Not Noise}
The wall-time collapse beyond 8 threads was observed independently across \emph{three} separate full experiment runs on this machine (two using the 1--20 ladder, one using the corrected 1--32 ladder reported here), with tight standard deviations at each collapsed configuration (e.g. 16 threads: $29{,}341 \pm 240$~ms here vs. $29{,}511\pm125$ and $29{,}609\pm249$~ms in the earlier runs). This rules out a one-off measurement artifact. This chip's Performance/Efficiency-core split relies on Intel Thread Director to steer OS scheduling decisions~\cite{intelhybrid2021}, and prior work on asymmetric multicore scheduling has shown that system software needs to be explicitly aware of this heterogeneity to avoid throughput loss~\cite{bilbao2023pmcsched}. The generic OpenMP thread pool used here, however, relies on default placement rather than explicit \texttt{OMP\_PLACES}/\texttt{proc\_bind} affinity control~\cite{eichenberger2012ompaffinity} — nothing pins threads to avoid oversubscribing contended siblings, so past 8 threads the scheduler appears to place work in a way that actively hurts throughput. Peak performance for both CPU variants occurs at exactly 4 threads, not at the nominal ``max thread'' count of 32 — a direct counter-example to assuming more threads is always better on heterogeneous desktop silicon, and the motivation for using 4 threads as the CPU backdrop for the GPU comparison above rather than 32. We note this optimum does not cleanly match the chip's topology (8 P-cores per Table~\ref{tab:hardware-rtx}, not 4), so we do not claim a confirmed topological explanation for why 4 specifically is optimal; without an $\texttt{OMP\_PROC\_BIND}$/$\texttt{OMP\_PLACES}$ control experiment we cannot rule out memory-bandwidth saturation or DVFS/thermal effects as contributing causes alongside scheduler oversubscription — we list this control experiment explicitly as future work (Section~\ref{sec:limitations}). Figure~\ref{fig:rtx-collapse} plots this scaling curve.

\subsection{GPU Speedup Against a Fair CPU Baseline}
With the CPU backdrop corrected, GPU V2 achieves $5{,}435$--$5{,}579$~ms end-to-end across all five grid configurations ($26.9$--$27.6$ FPS) — a $1.59\times$--$1.63\times$ speedup over CPU V1's own best configuration (4 threads, $8{,}844.17$~ms), not the inflated $4\times$+ figure that results from comparing against V1's single-threaded serial time or against the pathologically degraded 32-thread configuration. Using the same ``vs. best deterministic CPU configuration'' standard on both platforms (Section~\ref{sec:gb10-speedup}), this is a somewhat larger GPU advantage than on the GB10 ($1.46\times$ over CPU V1's best 20-thread configuration), consistent with the RTX 4090 being a discrete high-end GPU paired with a CPU whose deterministic (V1) parallel scaling is more constrained by the thread-scheduling collapse of Section~\ref{sec:rtx4090} than the GB10's CPU is.

\subsection{Warp Alignment Generalizes Across GPU Architectures}
At the CUDA-kernel level, the $32{\times}8$ grid remains the fastest Layer~8 kernel on this Ada Lovelace GPU ($358.14$~ms), $17.7\%$ faster than the standard $16{\times}16$ grid ($435.17$~ms) and $18.7\%$ faster than the slowest tested configuration ($440.70$~ms, $16{\times}16\_128$) — confirming that the warp-aligned memory-coalescing argument from Section~III-C — a direct consequence of the 32-thread warp granularity defined by the CUDA execution model~\cite{nvidiacudaguide} — is a property of CUDA itself, not an artifact specific to the GB10's Blackwell architecture or its LPDDR5x memory. Note, however, that at the \emph{wall-clock} level the five grid configurations remain statistically difficult to distinguish ($5{,}435$--$5{,}579\pm101$--$222$~ms, overlapping error bars) even though $32{\times}8$ nominally wins on both metrics in this run — the kernel-level advantage is only cleanly visible once CUDA-event profiling isolates it from CPU-side and run-to-run noise, reinforcing why Section~\ref{sec:methodology}'s fine-grained instrumentation is necessary rather than relying on wall-clock timing alone. \subsection{Non-Unified Memory Does Not Appear to Be a Bottleneck Here}
This platform's CPU and GPU memory are physically separate (63~GB system DDR vs. 24~GB GDDR6X VRAM over PCIe), unlike the GB10's single LPDDR5x pool over the memory-coherent NVLink-C2C interconnect~\cite{nvidiagracehopper2022} — the same architectural distinction recent work on unified physical memory for CPU-GPU accelerators has begun to study directly~\cite{wahlgren2025upm}. Despite this, GPU V2 still substantially outperforms every CPU configuration on this machine, and its Layer~8 kernel time ($358.14$~ms optimal) is faster in absolute terms than the GB10's own optimal kernel time ($541.59$~ms) — likely reflecting the RTX 4090's much larger raw compute throughput outweighing any PCIe transfer cost for a payload this small ($\approx$44~MiB of channel buffers per Table~\ref{tab:breakdown}'s VRAM figure) — discrete-GPU PCIe/DMA transfer is a well-documented bottleneck for other, more transfer-bound workloads~\cite{go2017apunet}, so its apparent absence here is plausibly payload-size-dependent rather than general. We did not capture a separate H2D/D2H breakdown on this platform in the current run; isolating that transfer cost explicitly (the way Table~\ref{tab:breakdown} does for the GB10) is needed before concluding the non-unified-memory hybrid CPU-GPU bottleneck is genuinely absent rather than simply small relative to this GPU's compute advantage.

\subsection{Precision Choice: FP64 and Its Performance Cost}
All V1/V2 arithmetic in this study, on both platforms, uses double-precision floating point (\texttt{double}), matching the original CPU baseline's data type and the $8$-byte-per-element buffer sizing throughout Section~II-C. We chose FP64 specifically to make the bit-exact CPU$\equiv$GPU comparison in Section~\ref{sec:methodology} as strict as possible: byte-for-byte equality across two independently-written CPU and CUDA implementations is a stronger claim in FP64 than it would be in FP32, where compiler and hardware fused-multiply-add and rounding-mode differences between CPU and GPU are more likely to introduce small numerical divergences even in a logically-equivalent computation. This choice has a real, quantifiable cost on the RTX 4090 specifically: as a consumer GPU, its FP64 throughput is architecturally limited to roughly $1/64$ of its FP32 throughput ($\approx 1.3$ vs. $\approx 82.6$ TFLOPS), so the $358.14$~ms optimal Layer~8 kernel time reported in Section~\ref{sec:rtx4090} is achieved while the GPU's dominant compute resource is almost entirely idle. We did not run an FP32 ablation, so we cannot report a corrected number, but based on the FP64:FP32 throughput ratio alone it is plausible that an FP32 (or mixed-precision) implementation would be substantially faster on this platform — at the cost of weakening the bit-exactness claim to a numerical-tolerance claim (e.g. PSNR/SSIM-based) rather than exact byte equality. The GB10's datacenter-class Blackwell GPU has a comparatively much smaller FP64:FP32 gap, so this trade-off is less severe there, but we did not separately quantify it. We list an FP32 ablation, with an explicit determinism-vs-throughput comparison, as future work (Section~\ref{sec:limitations}).

\section{Limitations and Future Work}
\label{sec:limitations}
This section consolidates the limitations noted throughout the paper and the concrete follow-up experiments each one motivates, ordered roughly by priority.
\begin{itemize}
    \item No competitive GPU baseline: Our V2 design is compared only against CPU implementations, not against alternative GPU formulations — an \texttt{atomicAdd}-based accumulation directly into the output buffer, an output-stationary gather kernel (one thread per output pixel, accumulating across channels in registers with zero intermediate buffer), or a cuDNN-based deconvolution (Section~III-B). Without these, we have shown spatial reduction is faster than a CPU baseline, not that it is the best available GPU design; implementing and benchmarking at least the atomic and gather variants is the highest-priority follow-up.
    \item FP64 throughout, unquantified FP32 trade-off: Section~\ref{sec:rtx4090} discusses why we used double precision (bit-exactness strictness) and that the RTX 4090's FP64 throughput is architecturally $1/64$ of its FP32 throughput, but we did not run an FP32 ablation to quantify the resulting speedup or the resulting numerical tolerance needed in place of exact bit-equality.
    \item Causal mechanism for warp alignment not directly profiled: Section~III-C's memory-coalescing explanation for the $32{\times}8$ grid's advantage is consistent with the measured timing difference but was not verified with hardware profiler counters (e.g. \texttt{ncu} global load efficiency); doing so, and extending the grid sweep to include non-warp-aligned widths such as $64{\times}4$, would let us distinguish a warp-width effect from other explanations.
    \item RTX 4090 thread-scheduling collapse not isolated from confounds: Section~\ref{sec:rtx4090} hypothesizes OS scheduler oversubscription (absent \texttt{OMP\_PROC\_BIND}/\texttt{OMP\_PLACES} affinity control) as the cause of the collapse past 8 threads, but we did not run the corresponding control experiment, and cannot yet rule out memory-bandwidth saturation, DVFS/thermal throttling, or false sharing as contributing or alternative causes.
    \item No H2D/D2H breakdown on the RTX 4090: Section~\ref{sec:rtx4090} reports only aggregate wall time and GPU kernel time for this platform; the same CUDA-event instrumentation used for the GB10 (Table~\ref{tab:breakdown}) was not run there, so we cannot yet directly compare transfer overhead between the unified and discrete-memory platforms — the central comparison the paper's title promises.
    \item Per-run correctness and kernel-time variance not captured: PSNR/SSIM are computed once per configuration against the final output file rather than for each of the 6 measured runs, and GPU Layer~8 kernel times are single representative profiled runs rather than 6-run means (Table~\ref{tab:benchmark} footnote); we cannot report a standard deviation for either, which weakens (though does not invalidate) the associated percentage claims.
    \item Single test sequence and resolution: All results use the 150-frame QCIF-to-CIF ($176{\times}144 \rightarrow 352{\times}288$) Suzie sequence. Testing additional resolutions (e.g. up to 1080p) would also shift the compute-to-transfer ratio and give the unified-vs-discrete-memory comparison more room to matter.
\end{itemize}

\section{Conclusion}

In this paper, we introduced a GPU Spatial Reduction framework for accelerating the 56-channel deconvolution reduction stage of FSRCNN super-resolution inference, and evaluated it on two architecturally distinct platforms rather than one. On both platforms, V1 (CPU spatial reduction) and V2 (GPU spatial reduction) are bit-exact against ground truth at every thread count and grid configuration tested ($\text{PSNR}=\infty$, $\text{SSIM}=1.0$), while V0's naive accumulation shows real, non-monotonic data-race corruption (as low as $13.8$~dB/$0.518$ SSIM on the GB10; Fig.~\ref{fig:correctness}). On the NVIDIA GB10 Grace Blackwell Superchip (ASUS Ascent GX10), the optimal $32{\times}8$ warp-aligned CUDA grid achieves a $1.46\times$ speedup ($31.5$ FPS) over CPU V1's best correctness-verified configuration; against a single-threaded serial baseline, the figure is a larger but less representative $4.53\times$, which we report only as a secondary, explicitly-labeled comparison (Section~\ref{sec:gb10-speedup}). CUDA event profiling shows the GPU Layer~8 kernel completing in $541.59$~ms ($3.61$~ms/frame) while also surfacing a $516.74$~ms host-to-device transfer asymmetry (Section~\ref{sec:nvlink}) as a concrete optimization target. Cross-platform validation on a discrete-GPU desktop (Intel i9-14900K + NVIDIA RTX 4090, Section~\ref{sec:rtx4090}) confirms the warp-aligned $32{\times}8$ grid remains fastest at the kernel level on a second GPU architecture (Ada Lovelace), and that GPU V2 outperforms that platform's best correctness-verified CPU configuration by up to $1.63\times$ despite its physically separate (non-unified) CPU and GPU memory — while also surfacing a CPU thread-scheduling pathology on heterogeneous P-core/E-core silicon that is a confound for any CPU baseline on such hardware, independent of our GPU contribution. Section~\ref{sec:limitations} lists the follow-up experiments (competitive GPU baselines, an FP32 ablation, RTX 4090 transfer-cost instrumentation, and a scheduler-affinity control experiment) needed to fully close out these findings.
