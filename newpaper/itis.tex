\begin{abstract}
Convolutional Neural Network (CNN) super-resolution models such as FSRCNN suffer from a severe computational bottleneck in their final deconvolution layer, where naive multi-threaded CPU accumulation causes data races and non-reproducible output corruption. We propose a GPU Spatial Reduction strategy that offloads FSRCNN's Layer~8 deconvolution to isolated per-channel CUDA kernels followed by a parallel reduction pass, eliminating races by construction, and evaluate it on two architecturally distinct platforms: the NVIDIA GB10 Grace Blackwell Superchip (unified memory over NVLink-C2C) and a discrete-GPU desktop (Intel i9-14900K with an NVIDIA RTX 4090 over PCIe). On both platforms, V1 and V2 output is byte-for-byte identical to a verified deterministic reference at every configuration tested, and the GPU output is further bit-identical across the two platforms directly ($0$ differing bytes, matching SHA-256 digests) despite differing host ISA and GPU microarchitecture. Timings are reported as mean $\pm$ SD over the 6 measured runs of a 7-run repetition. The warp-aligned $32{\times}8$ CUDA grid is fastest at the kernel level on both GPU architectures, and per-kernel event profiling localizes the entire gain to the deconvolution kernel, exactly where the coalescing explanation predicts it. Against each platform's best correctness-verified CPU configuration, GPU offloading achieves $1.46\times$ (GB10, $31.5$ FPS) and up to $1.63\times$ (RTX 4090, $27$--$27.6$ FPS) speedups; against the fastest bit-exact serial run the secondary figure is $3.84\times$ on the GB10. The determinism guarantee costs $4.6\%$ of GPU Layer~8 time on the GB10 but only $0.6\%$ on the RTX 4090, a gap traceable to whether the private buffer fits in last-level cache; conversely, device-to-host transfer is $4.74\times$ faster on unified memory. Against a constructed high-resolution reference the pipeline gains $2.17$~dB PSNR-Y over bicubic upscaling. These results establish spatial reduction as a deterministic, cross-platform-portable pattern for GPU-accelerated CNN inference.
\end{abstract}

\section{Introduction}

Edge and workstation-class AI hardware increasingly adopt SoCs where multicore CPUs and GPUs co-exist on high-speed interconnects~\cite{shi2016edge,zhou2019edge}. Super-resolution CNNs progressed from early formulations~\cite{dong2014srcnn} to FSRCNN~\cite{dong2016fsrcnn}, which achieves high quality by deferring feature extraction to low-resolution space and upscaling only at the final deconvolution layer.

That final stage (Layer~8) imposes a disproportionate computational burden: for $2\times$ upscaling ($176{\times}144 \rightarrow 352{\times}288$), it applies a $9{\times}9$ kernel across 56 channels and accumulates them into one output plane. Parallelizing this on multicore CPUs creates a dilemma: naive shared-memory accumulation causes data races and non-reproducible pixel corruption~\cite{annisa2025}, while mutex/atomic synchronization causes prohibitive lock contention. The spatial reduction pattern avoids both by writing to private per-channel buffers and reducing them in a separate deterministic pass. That said, 56 private high-resolution buffers incur real memory overhead on CPU.

We offload this deconvolution and spatial reduction to CUDA kernels on an NVIDIA GPU while parallelizing Layers 1--7 across CPU cores, achieving high throughput, memory isolation, and deterministic bit-exactness. Our contributions:
\begin{enumerate}
    \item GPU Cost-Profile Shift: privatization-reduction is a classical pattern, not a new algorithm; we show that moving it to the GPU changes its cost profile qualitatively. The $43.3$~MiB of private-buffer traffic that costs $8$--$18\%$ of CPU wall time is absorbed instead by GPU memory bandwidth and thread parallelism, while the result stays bit-exact with the CPU implementation. We frame this as a shift in bandwidth and parallelism rather than in memory capacity because our primary platform has no separate VRAM: the GB10's $128$~GB LPDDR5x pool is shared by CPU and GPU, so the buffer does not move anywhere, only the computation over it does.
    \item Warp-Aligned Grid Configuration: a $32{\times}8$ thread block maximizes memory coalescing for the deconvolution's row-major access, cutting Layer~8 kernel time $22.8\%$ (GB10) and $17.7\%$ (RTX 4090).
    \item Rigorous Statistical Evaluation: on the GB10, GPU output is byte-for-byte identical to the CPU baseline ($\text{diff\_bytes}=0$) at every configuration tested, and timing measured over 7-run repetitions gives a $1.46\times$ speedup over the best deterministic CPU configuration (20 threads).
    \item Cross-Platform Validation: an independent replication on discrete-PCIe hardware (Intel i9-14900K + RTX 4090) confirms bit-exactness and warp-alignment generalize beyond the GB10, and GPU V2's output is bit-identical ($0$ differing bytes, matching SHA-256) across both platforms directly, not just within each; this also surfaces a CPU thread-scheduling pathology on heterogeneous P/E-core silicon (Section~\ref{sec:rtx4090}).
\end{enumerate}

\section{Background and Baseline Architecture}

\subsection{Related Work}
CNN super-resolution progressed from early formulations~\cite{dong2014srcnn} to FSRCNN~\cite{dong2016fsrcnn}, increasingly deployed on heterogeneous CPU+GPU SoCs~\cite{shi2016edge,zhou2019edge}. Closest to ours, Annisa et al.~\cite{annisa2025} empirically characterize the same FSRCNN Layer~8 race condition on an Orange Pi~5 (Rockchip RK3588S: 4$\times$ Cortex-A76 big $+$ 4$\times$ Cortex-A55 LITTLE, the same Suzie $176{\times}144\rightarrow352{\times}288$ sequence we use), finding race-induced corruption more severe on LITTLE-CPU affinity configurations than on big-CPU ones; their focus is on characterizing that corruption across core-affinity settings rather than on an algorithmic remedy for it. We do not compare speedup figures directly, since our hardware (GB10/RTX 4090) differs from theirs (Orange Pi 5) by orders of magnitude in core count and class. Privatize-then-reduce is a classical parallelization pattern rather than a new algorithm; our contribution is adopting it as a race-free CPU baseline (V1) and then moving it to the GPU (V2), which changes its cost profile qualitatively while staying bit-exact with the CPU reference. CNN inference on ARM big.LITTLE clusters scales well under proper scheduling~\cite{wang2020pipeit}, supporting our GB10 CPU baseline as non-trivial (Section~\ref{sec:gb10-speedup}). General-purpose libraries like cuDNN~\cite{chetlur2014cudnn} target convolution broadly but not this specific race-free layout (Section~III-B); we do not claim to outperform them, only to control the memory layout. Discrete-GPU PCIe transfer overhead is well documented~\cite{go2017apunet}, motivating our unified-vs-discrete memory comparison (Section~\ref{sec:rtx4090}); recent work characterizes unified physical memory for CPU-GPU accelerators directly~\cite{wahlgren2025upm}. Our RTX 4090 thread-scheduling collapse (Section~\ref{sec:rtx4090}) relates to prior work on asymmetric-CPU scheduling~\cite{bilbao2023pmcsched,eichenberger2012ompaffinity}; our contribution is an empirical observation, not a new mechanism.

\subsection{FSRCNN Architecture}
FSRCNN consists of eight layers: Feature Extraction (Layer 1), Shrinking (Layer 2), four Mapping layers (Layers 3--6), Expanding (Layer 7), and Deconvolution (Layer 8). For an input sequence at $176{\times}144$ scaled by $2\times$, Layers 1--7 operate in low-resolution ($176{\times}144$) space, outputting 56 feature maps. Layer~8 receives these 56 channels, applies a $9{\times}9$ transposed convolution~\cite{dumoulin2016convolution} with stride 2, and reduces them into a $352{\times}288$ YUV luminance output frame.

\subsection{Baseline Variants}
We analyze three distinct algorithmic variants:
\begin{itemize}
    \item V0 (Naive OpenMP CPU): Implemented in \texttt{fsrcnn\_parallel.c}. Layer~8 worker threads accumulate deconvolution outputs directly into a shared single output buffer \texttt{img\_fltr\_8}. When executed with $\text{threads} > 1$, overlapping kernel footprints cause unsynchronized read-modify-write data races, leading to output corruption, the class of bug that dynamic race detectors such as ThreadSanitizer~\cite{serebryany2009threadsanitizer} are designed to catch.
    \item V1 (Spatial Reduction CPU): Implemented in \texttt{fsrcnn\_parallel\_spatial\_reduction.c}. Eliminates data races by allocating a private intermediate buffer $\text{all\_tmp}[56 \times 352 \times 288 \times 8\,\text{B}]$ ($43.3$~MiB). Each channel writes to its own isolated offset. A second pass then sums the 56 channels per pixel. Both passes are parallel, but along different axes: the deconvolution is threaded over channels, the reduction over output pixels. The reduction needs no synchronization because each output pixel is written by exactly one thread, and it stays deterministic because that thread accumulates its 56 summands in fixed channel order regardless of how the loop is scheduled.
    \item V2 (GPU Spatial Reduction - Proposed): Implemented in \texttt{fsrcnn\_gpu\_main.cu} and \texttt{fsrcnn\_gpu.cu}. Layers 1--7 are parallelized across CPU cores using OpenMP, while Layer~8 deconvolution and channel reduction are offloaded to CUDA kernels on the NVIDIA Blackwell GPU.
\end{itemize}

\subsection{CUDA Kernel Design and Warp Alignment}
We implement Layer~8 as two specialized hand-written CUDA kernels rather than using a general-purpose library such as cuDNN~\cite{chetlur2014cudnn}. We do not claim this is faster than a cuDNN-based deconvolution (untested, and a well-tuned library kernel could plausibly win); we only claim that it gives direct control over the private-buffer-plus-reduction layout central to our correctness argument. A head-to-head comparison against cuDNN and simpler alternatives (\texttt{atomicAdd}, output-stationary gather) is future work (Section~\ref{sec:limitations}); our result shows this design is faster and race-free relative to the CPU baseline, not that it is the fastest possible GPU design.

\subsubsection{Deconvolution Kernel (\texttt{deconv\_kernel})}
Each CUDA thread block processes a 2D tile of the input feature map. For each channel $c \in [0, 55]$, threads compute the $9{\times}9$ transposed convolution and store the result directly into an isolated channel plane inside GPU VRAM buffer \texttt{d\_all\_tmp}, indexed as $\text{index}(c, y, x) = c \times (H_{out} \times W_{out}) + y \times W_{out} + x$.

\subsubsection{Spatial Reduction Kernel (\texttt{spatial\_reduction\_kernel})}
After deconvolution completes, the spatial reduction kernel assigns one CUDA thread per high-resolution output pixel $(y, x)$. The thread iterates across all 56 channel planes in \texttt{d\_all\_tmp}, sums the values, and adds the Layer~8 bias:
\begin{equation}
\text{output}[y, x] = \left( \sum_{c=0}^{55} \text{d\_all\_tmp}[c, y, x] \right) + \text{bias}_8
\end{equation}

Because channel writes are fully isolated during deconvolution and read-only during reduction, the execution is completely race-free and deterministic.

NVIDIA GPUs execute threads in SIMD groups of 32 called \emph{warps}~\cite{nvidiacudaguide}. Standard $16{\times}16$ blocks place only 16 threads along the row-major X dimension, causing consecutive warps to straddle non-contiguous memory rows. Since warp/block sizing has a first-order effect on SIMT throughput~\cite{lashgar2012warpresize}, we evaluate a $32{\times}8$ block (256 threads): setting $B_x=32$ guarantees all 32 threads in a warp access contiguous doubles along one image row, maximizing coalescing.

\section{Experimental Evaluation}

\subsection{Evaluation Methodology}
\label{sec:methodology}
Experiments were conducted on the ASUS Ascent GX10 under Ubuntu 24.04 LTS ARM64. The workload consists of 150 frames of the Suzie video sequence ($176{\times}144 \rightarrow 352{\times}288$, YUV420p).

To guarantee statistical rigor, every configuration was executed for 7 repetitions: run 1 discarded as cold-start/warmup, runs 2--7 (6 runs) recorded as Mean $\pm$ SD.

\emph{Reproducibility:} CPU binaries are compiled with \texttt{gcc -fopenmp -O3} (no \texttt{-march=native}/\texttt{-ffast-math}); parallel loops use plain \texttt{\#pragma omp parallel for} with no explicit \texttt{schedule()}, so thread placement follows the OpenMP runtime's default (GNU \texttt{libgomp}: static). The GPU binary is compiled with \texttt{nvcc -O3 -std=c++11 -arch=native}, which resolves to \texttt{sm\_121} on the GB10 and \texttt{sm\_89} on the RTX 4090. GCC 13.3.0 (Ubuntu 24.04) was used on both platforms, and both use CUDA release 13.0, differing only in patch level (\texttt{V13.0.88} on the GB10 vs. \texttt{V13.0.48} on the RTX 4090; Table~\ref{tab:hardware}). All V1/V2 arithmetic uses double precision (\texttt{double}), matching the CPU baseline and making the bit-exact CPU$\equiv$GPU comparison below as strict as possible; FP32 would admit more CPU/GPU rounding divergence even for a logically-equivalent computation (RTX-specific throughput consequence in Section~\ref{sec:rtx4090}).

\emph{Reference file:} We generate one verified deterministic reference, \texttt{ground\_truth.yuv}, by running V1 (race-free by construction) single-threaded once; since V0, V1, and V2 implement the identical FSRCNN algorithm and differ only in execution strategy, this file is an internal determinism check, not an independently sourced high-resolution ground truth. Correctness is assessed two ways: a direct byte comparison (\texttt{cmp -l}) between V1 and V2 output ($\text{diff\_bytes}=0$ across all grid configurations), and scoring each variant against this reference via byte diff, PSNR, and SSIM~\cite{wang2004ssim} (\texttt{ffmpeg}). V1/V2's PSNR$=\infty$/SSIM$=1.0$ against it is thus logically equivalent to the \texttt{cmp -l} result, not a separate quality measurement; we report it as \emph{bit-exact} rather than a numeric figure (Tables~\ref{tab:benchmark}, \ref{tab:rtx-benchmark}). This confirms cross-variant determinism, not how close FSRCNN's reconstruction is to the true high-resolution Suzie sequence; Section~\ref{sec:quality} addresses that separately with a constructed high-resolution reference.

Unless stated otherwise, PSNR/SSIM figures in Tables~\ref{tab:benchmark} and~\ref{tab:rtx-benchmark} are \texttt{ffmpeg}'s all-component average over Y, U and V. Because only the Y plane passes through the network, the untouched chroma planes score identically to the reference and pull the average upward: the RTX 4090's worst V0 case reads $23.0$~dB/$0.845$ all-component but $21.5$~dB/$0.767$ on luminance alone. The all-component figures therefore \emph{understate} the corruption, which does not weaken the determinism argument, but we give luminance-only numbers wherever the magnitude of the degradation is what matters (Fig.~\ref{fig:correctness}, Section~\ref{sec:quality}).

V0, in contrast to V1/V2, shows real, non-monotonic degradation from its data race against the same file: as low as $13.8$~dB/$0.518$ on the GB10 (4 threads), and, more strikingly, $68.6$~dB/$0.99996$ on the RTX 4090 (4 threads) before collapsing to $23.0$~dB/$0.845$ at 32 threads. The RTX case matters more: a race degrading output by only $68.6$~dB is invisible to casual inspection or a coarse PSNR threshold, yet exactly as non-deterministic as the $13.8$~dB case, an argument for determinism-by-construction over statistical trust that runs ``look fine.'' The non-determinism is directly observable: three consecutive V0 runs at 32 threads on the RTX 4090 corrupted $4.75$, $5.01$ and $5.04$~million of $22.8$~million output bytes, scoring $21.34$, $21.46$ and $21.63$~dB PSNR-Y --- never the same output twice. Fig.~\ref{fig:correctness} shows this directly (reference, V1, V2 visually identical; V0 shows clear scanline corruption from unsynchronized writes to \texttt{img\_fltr\_8}).

\subsection{Reconstruction Quality Against a True High-Resolution Reference}
\label{sec:quality}
Every correctness figure reported so far is a self-consistency check: V2 against V1, which is why it reads ``bit-exact'' rather than a PSNR value. That establishes the GPU port is faithful to the CPU algorithm, but it says nothing about whether FSRCNN reconstructs anything, because no high-resolution ground truth exists anywhere in the pipeline --- \texttt{suzie\_qcif.yuv} is the input, not a downsampled version of something larger.

We therefore constructed the missing reference. Suzie was bicubic-downsampled from $176{\times}144$ to $88{\times}72$, that sequence was fed to the same FSRCNN pipeline at scale 2 to reconstruct $176{\times}144$, and the result was scored against the original $176{\times}144$ frames. Bicubic upscaling of the same $88{\times}72$ input is the comparator: it is what the network has to beat to justify its runtime. We report luminance-only figures, since only the Y plane passes through the network (chroma is $2\times$ pixel replication in this implementation), and an all-component average would credit FSRCNN for a replication step it does not perform.

FSRCNN reaches $37.86$~dB PSNR-Y and $0.9665$ SSIM-Y, against bicubic's $35.69$~dB and $0.9532$: a gain of $2.17$~dB and $0.0133$ SSIM over the whole 150-frame sequence. The network earns its cost. Two caveats belong with that number. It is measured on one sequence at one scale factor, so it is a sanity check on the pipeline rather than a claim about FSRCNN's quality in general, which is established in the original work~\cite{dong2016fsrcnn}. And on the chroma planes bicubic is in fact \emph{better} ($50.45$/$49.71$~dB against $48.56$/$47.48$~dB), precisely because it interpolates U and V while our pipeline replicates them --- a limitation of this implementation, not of spatial reduction, and one that would be worth fixing before deploying the pipeline for perceptual quality rather than throughput measurement.

\subsection{The Cost of Determinism, Quantified}
\label{sec:cost-of-determinism}
Contribution 1 (Section~I) claims that privatization-reduction is expensive on the CPU and absorbed by the GPU. Tables~\ref{tab:benchmark} and \ref{tab:rtx-benchmark} let us quantify the CPU side directly as the wall-time delta between V0 (racy, no privatization) and V1 (privatized, deterministic) at matched thread counts. On the GB10: $+18.2\%$ at 1 thread ($18{,}240.50\rightarrow21{,}552.33$~ms), $+17.6\%$ at 4 threads ($7{,}074.33\rightarrow8{,}316.50$~ms), $+9.1\%$ at 20 threads ($6{,}346.33\rightarrow6{,}921.83$~ms). On the RTX 4090: $+9.2\%$ at 1 thread ($20{,}973.50\rightarrow22{,}904.17$~ms), $+7.8\%$ at 4 threads ($8{,}207.67\rightarrow8{,}844.17$~ms). This delta isolates privatization specifically rather than a difference in how much of the work is threaded: V0 and V1 parallelize the same deconvolution, and V1's additional reduction pass is itself parallel over output pixels (Section~II-C), so the gap measures the cost of writing and re-reading $43.3$~MiB of private buffers, not the cost of serializing a stage. Determinism therefore costs $8$--$18\%$ of CPU wall time. The GB10 points suggest the cost falls once the machine is saturated, but 1 thread and 4 threads are nearly identical there ($18.2\%$ vs. $17.6\%$), so this is a two-level effect at best, not a smooth trend.

On the GPU side the same $43.3$~MiB of private-buffer traffic carries no measurable wall-time penalty: the $32{\times}8$ kernel still wins outright (Section~\ref{sec:gb10-speedup}) with peak device memory bounded at $44.3$~MiB including allocator padding, well under $0.1\%$ of the $128$~GB the GB10's CPU and GPU share or of the RTX 4090's $24$~GB of dedicated VRAM. We state this as a bandwidth-and-parallelism result rather than a capacity result, because on the GB10 there is no separate VRAM for the buffer to move into.

Per-kernel event instrumentation (Section~\ref{sec:breakdown}) now lets us put the GPU-side cost in the same units as the CPU-side $8$--$18\%$. The reduction pass is the GPU analogue of the privatization overhead, and it accounts for $4.6\%$ of the Layer~8 event window on the GB10 and $0.6\%$ on the RTX 4090 --- in both cases well below what the same determinism guarantee costs on the CPU, and on the discrete GPU almost free. The reason the two platforms differ so much is architectural rather than algorithmic: the reduction is bandwidth-bound, and the RTX 4090's L2 is large enough to hold the entire private buffer (Section~\ref{sec:breakdown}). Determinism-by-construction is therefore cheapest exactly where cache capacity exceeds the privatization working set, which is a useful design rule for anyone applying this pattern to a larger network: the overhead scales with how far the private buffer overflows the last-level cache, not with the channel count as such.

\subsection{Fine-Grained GPU Timing Breakdown}
\label{sec:breakdown}
To evaluate each stage's contribution we instrumented CUDA Event profiling inside \texttt{fsrcnn\_gpu\_main.cu}, and ran the optimal configuration ($32{\times}8\_256$) six times on each platform. Table~\ref{tab:breakdown} reports the result for both.

\emph{A correction to how we previously read this instrumentation.} An earlier draft of this work treated the host-side counter \texttt{h2d\_ms} as a disjoint slice of wall time and reported host-to-device transfer as $516.74$~ms, roughly $11\%$ of the pipeline. That reading was wrong, and the six-run sweep makes the error visible. The counter accumulates host wall time spent inside \texttt{cudaMemcpy}, but those copies are issued \emph{inside} the CUDA-event window that \texttt{gpu\_l8\_ms} measures, and a blocking copy on the default stream cannot begin until the previously launched kernel has drained. \texttt{h2d\_ms} therefore charges kernel-completion waiting to transfer, and double-counts time already inside \texttt{gpu\_l8\_ms}. The decisive evidence is that \texttt{h2d\_ms} tracks \texttt{gpu\_l8\_ms} at a nearly fixed ratio across all five grid configurations ($0.96$--$0.98$ on the GB10, $0.88$--$0.90$ on the RTX 4090) and moves by $167$~ms on the GB10 when the \emph{kernel block shape} alone changes, even though the transferred byte count is identical in every configuration. No genuine transfer measurement behaves that way. We report the corrected decomposition below and no longer make the ``H2D asymmetry'' claim that rested on the old reading (Section~\ref{sec:nvlink}).

The corrected split comes from bracketing each \texttt{deconv\_kernel} launch and the \texttt{spatial\_reduction\_kernel} with their own CUDA events, which also resolves the separation Section~\ref{sec:cost-of-determinism} needed. Residual in-window time (real transfer, launch gaps, and host-side padding between launches) is reported as its own line rather than folded into either kernel.

Two results stand out, and they point in opposite directions.

First, the reduction kernel costs $26.32$~ms on the GB10 but only $2.62$~ms on the RTX 4090, a $10.0\times$ gap far larger than any general compute advantage (\texttt{deconv\_kernel} differs by only $1.6\times$). The reduction is purely bandwidth-bound: it reads the whole $43.31$~MiB private buffer once per frame, $6.81$~GB over 150 frames. That works out to $259$~GB/s on the GB10, about $95\%$ of the $273$~GB/s theoretical peak of its LPDDR5x pool, and to $2{,}597$~GB/s on the RTX 4090, which \emph{exceeds} that card's $1{,}008$~GB/s of GDDR6X bandwidth by more than $2.5\times$. A DRAM-resident working set cannot produce that number. The natural explanation is the RTX 4090's $72$~MB L2 cache: the $43.31$~MiB buffer fits inside it, so the reduction is served largely from cache, whereas the GB10 must stream the same buffer from its unified memory pool at close to hardware peak. We offer this as the reading most consistent with the measured bandwidths rather than a profiled fact, since we did not capture L2 hit-rate counters (Section~\ref{sec:limitations}).

Second, device-to-host transfer runs the other way: $3.46$~ms on the GB10 against $16.42$~ms on the RTX 4090, a $4.74\times$ advantage for unified memory on identical payloads ($35.1$ vs. $7.4$~GB/s effective). This is the cleanest unified-versus-discrete contrast in our data, and unlike the retracted H2D figure it is measured outside the event window, after \texttt{cudaEventSynchronize}, with no kernel execution to conflate it with.

Peak device memory stayed bounded at $45{,}382$~KiB ($\approx44.3$~MiB) on both platforms across every GPU configuration, about 1~MiB above the $43.3$~MiB theoretical minimum (Section~II-C), consistent with modest allocator padding.

\section{Discussion and Key Insights}

\subsection{Speedup vs. Maxed-Out CPU Cores, and Warp Alignment}
\label{sec:gb10-speedup}
We report GPU speedup against CPU V1, not V0, at multi-thread configurations: V1 is race-free by construction at every thread count, while V0 is only \emph{incidentally} correct at 1 thread (no concurrency to race on) and degrades with more threads (Table~\ref{tab:benchmark}). V0 is in fact the raw-wall-time winner at 20 threads ($6{,}346.33$~ms, faster than V1 and giving only $1.33\times$ GPU speedup if used), but we exclude it as a baseline since its output there is not verified correct; we state the number here rather than omitting it.

GPU V2 ($32{\times}8\_256$) reaches $4{,}756.33$~ms end-to-end ($31.5$ FPS). Against CPU V1's 20-thread configuration ($6{,}921.83$~ms, the fastest correctness-verified CPU result) this is $1.46\times$ ($46\%$ faster), our primary headline figure, consistent with how we report the RTX 4090 (Section~\ref{sec:rtx4090}).

The serial comparison needs more care, because the two variants do not share a serial baseline. At 1 thread V0 is bit-exact (Table~\ref{tab:benchmark}) and also faster than V1 ($18{,}240.50$ vs. $21{,}552.33$~ms), since it skips the privatization V1 pays for. V0 at 1 thread is therefore the fastest \emph{bit-exact} serial baseline available, and the defensible serial figure is the one measured against it: $3.84\times$ on the GB10, and $3.86\times$ on the RTX 4090 ($20{,}973.50/5{,}435.50$). Measuring against V1's serial time instead yields the larger $4.53\times$ and $4.21\times$; that choice keeps the denominator inside one variant family, but the slower denominator is what makes the ratio bigger, so we lead with $3.84\times$ and report $4.53\times$ only as the within-variant figure.

This $1.46\times$ is notable given CNN inference scales well on ARM big.LITTLE clusters when properly scheduled~\cite{wang2020pipeit}; the GB10 CPU baseline is not a strawman. GPU V2 also has lower variance ($\pm30.71$~ms) than CPU V1 at its own best configuration (20 threads, $\pm82.49$~ms, $2.7\times$ higher) or at its noisiest (8 threads, $\pm998.43$~ms). Figure~\ref{fig:thread-scaling}(a) plots both CPU variants across the full thread ladder: unlike the RTX 4090 (Fig.~\ref{fig:thread-scaling}(b)), the GB10's 20 homogeneous cores (no SMT) scale smoothly with no collapse.

Shifting from the default $16{\times}16$ grid ($696.51 \pm 1.78$~ms kernel time, 6 runs) to the warp-aligned $32{\times}8$ grid ($533.19 \pm 2.58$~ms) reduces Layer~8 kernel time by $163.32$~ms ($23.4\%$). The separation exceeds fifty standard deviations, so unlike the wall-clock comparison this is not a marginal effect.

We attribute it to memory coalescing: a 32-thread-wide block lets every thread in a warp issue a request into the same coalesced transaction, rather than splitting it across multiple transactions as a 16-wide block does. The per-kernel breakdown supports this more sharply than wall time can. Block shape is a property of \texttt{deconv\_kernel} only --- \texttt{spatial\_reduction\_kernel} is launched one-dimensionally and is unaffected by the grid parameter --- so if coalescing is the mechanism, the entire gain must appear in the deconvolution and none in the reduction. That is what we measure: going from $16{\times}16$ to $32{\times}8$, \texttt{deconv\_kernel} drops $24.9\%$ ($564.74 \pm 0.75$ to $424.07 \pm 0.76$~ms) while \texttt{spatial\_reduction\_kernel} moves by $+0.9\%$ ($26.08$ to $26.32$~ms), within its own run-to-run spread. The improvement is localized exactly where the mechanism predicts. This remains an inference from timing rather than a direct measurement of load efficiency (e.g. via \texttt{ncu} counters), and a sweep including non-aligned widths would strengthen it further (Section~\ref{sec:limitations}).

\subsection{Transfer Cost and Amdahl's Law}
\label{sec:nvlink}
With the measurement error in Section~\ref{sec:breakdown} corrected, transfer is not the bottleneck we previously took it for. On the GB10, everything inside the event window that is not kernel execution --- real host-to-device traffic, launch gaps, and the host-side padding done between launches --- totals $127.65$~ms, or $2.7\%$ of wall time, and device-to-host adds a further $3.46$~ms ($0.023$~ms/frame). Even treating that entire residual as pure transfer, which overstates it, moves under $3\%$ of the pipeline. The corresponding residual on the RTX 4090 is larger in both absolute and relative terms ($152.14$~ms, $2.8\%$ of a longer wall time, and $36.5\%$ of its event window against the GB10's $22.1\%$), which is the direction PCIe versus NVLink-C2C would predict, though the margin is small enough that we do not lean on it. The one transfer measurement that is both clean and clearly asymmetric is D2H, where unified memory is $4.74\times$ faster (Section~\ref{sec:breakdown}).

What Table~\ref{tab:breakdown} shows instead is a straightforward Amdahl's Law~\cite{amdahl1967} ceiling. Offloading Layer~8 shrank it to $533.19$~ms ($3.55$~ms/frame), $11.2\%$ of wall time on the GB10 and just $6.6\%$ on the RTX 4090, while CPU Layers 1--7 --- still running on 20 and 4 OpenMP threads respectively, not serial --- now account for $71.4\%$ and $84.5\%$. The accelerated stage has been optimized into near-irrelevance, and further tuning of Layer~8 cannot buy much: even making it free would leave the RTX 4090 pipeline at $93\%$ of its current wall time. Offloading Layers 1--7 is therefore the only remaining path to sub-second reconstruction, and a Roofline analysis~\cite{williams2009roofline} would clarify whether that offload is compute- or memory-bound first. The unaccounted remainder is process launch, file I/O, and the per-frame \texttt{uint8}$\leftrightarrow$\texttt{double} conversion loops, all of which sit outside the instrumented region and all of which are single-threaded. It is larger on the GB10 in both absolute and relative terms ($821.20$~ms, $17.3\%$, against $469.33$~ms, $8.6\%$), which is consistent with that serial host code running on a $3.9$~GHz ARM core rather than a $6.0$~GHz x86 one; we did not instrument it separately to confirm.

\section{Cross-Platform Validation on Discrete-GPU Hardware}
\label{sec:rtx4090}

To test whether the GPU Spatial Reduction approach generalizes beyond the GB10's unified-memory architecture, we replicated the experiment on a conventional discrete-GPU desktop (Intel Core i9-14900K + NVIDIA RTX 4090; specifications in Table~\ref{tab:hardware}), where CPU (system DDR) and GPU (VRAM) memory are physically separate and connected over PCIe rather than NVLink-C2C. Unlike the GB10's 20 homogeneous-per-tier ARM cores with no simultaneous multithreading (SMT), this CPU has a heterogeneous 8~Performance-core~+~16~Efficiency-core layout where only the P-cores support Hyper-Threading, yielding 24 physical / 32 logical threads.

We therefore (1) swept a topology-correct ladder (1, 2, 4, 8, 16, 24, 32, matching this chip's core boundaries) and (2) used this platform's own best CPU configuration (4 threads) as the backdrop, rather than assuming more threads is optimal. \subsection{The Collapse Is Reproducible, and GPU Speedup Against a Fair Baseline}
The collapse was observed independently across \emph{three} separate full runs (two on the 1--20 ladder, one on the corrected 1--32 ladder reported here), with tight SDs at each collapsed point (e.g. 16 threads: $29{,}341\pm240$~ms here vs. $29{,}511\pm125$ and $29{,}609\pm249$~ms previously), which rules out a one-off artifact. This chip's P/E-core split relies on Intel Thread Director for scheduling, and asymmetric-CPU system software generally needs explicit heterogeneity awareness to avoid throughput loss~\cite{bilbao2023pmcsched}; the generic OpenMP pool used here has no such affinity control~\cite{eichenberger2012ompaffinity} (\texttt{OMP\_PLACES}/\texttt{proc\_bind}), so past 8 threads the scheduler appears to actively hurt throughput. Peak performance is at exactly 4 threads, not the nominal 32-thread maximum. This optimum does not cleanly match the chip's topology (8 P-cores, Table~\ref{tab:hardware}), so we do not claim a confirmed topological explanation, and cannot rule out memory-bandwidth or DVFS/thermal effects without a control experiment (Section~\ref{sec:limitations}). Figure~\ref{fig:thread-scaling}(b) plots this curve.

With the CPU backdrop corrected, GPU V2 reaches $5{,}435$--$5{,}579$~ms end-to-end ($26.9$--$27.6$ FPS), a $1.59\times$--$1.63\times$ speedup over CPU V1's best configuration (4 threads, $8{,}844.17$~ms), not the inflated $4\times$+ figure from comparing against V1's serial time or the degraded 32-thread configuration. Using the same ``best deterministic CPU'' standard on both platforms (Section~\ref{sec:gb10-speedup}), this is somewhat larger than the GB10's $1.46\times$, consistent with V1's parallel scaling here being more constrained by the thread-scheduling collapse than the GB10's CPU is.

\subsection{Cross-Architecture Bit-Exactness}
\label{sec:cross-arch-bitexact}
Section~\ref{sec:methodology} and Table~\ref{tab:rtx-benchmark} each establish bit-exactness \emph{within} a platform (CPU V1 $\equiv$ GPU V2, separately, on the GB10 and on the RTX 4090). A stronger and separate question is whether GPU V2's output is identical \emph{across} platforms. The GB10 (ARM host, Blackwell \texttt{sm\_121}) and the RTX 4090 (x86 host, Ada Lovelace \texttt{sm\_89}) differ in host instruction set architecture and GPU microarchitecture, so bit-identical output is not guaranteed by IEEE-754 \texttt{double} compliance alone: code generation for two different SM targets, FMA (fused multiply-add) contraction, and math-library implementations can still diverge in the last bit. We note that the two toolchains are otherwise closely matched (GCC 13.3.0 and CUDA 13.0 on both, differing only in CUDA patch level), so this test isolates the ISA and microarchitecture difference rather than compounding it with a major toolkit-version difference; a cross-\emph{toolkit} determinism claim would need a separate experiment. We ran the winning $32{\times}8$ configuration on both platforms and compared the raw output files directly: \texttt{cmp -l} reports $0$ differing bytes, and the SHA-256 digests of both files are identical (\texttt{8db2c07a...ca066b}). GPU V2's output is therefore bit-identical not only to its own platform's CPU reference, but across two GPU architecture generations and two host CPU instruction set architectures, the strongest form of the determinism claim this paper makes.

\subsection{Warp Alignment Generalizes Across GPU Architectures}
\label{sec:warp-generalize}
At the kernel level, $32{\times}8$ remains fastest on this Ada Lovelace GPU ($360.92 \pm 7.22$~ms over 6 runs), $17.4\%$ faster than $16{\times}16$ ($437.06 \pm 3.86$~ms) and $17.5\%$ faster than the slowest configuration ($437.49 \pm 3.46$~ms), confirming the warp-aligned coalescing argument from Section~III-B (a consequence of CUDA's 32-thread warp granularity~\cite{nvidiacudaguide}) is a property of CUDA itself, not specific to the GB10. The same localization holds here: \texttt{deconv\_kernel} falls $15.6\%$ ($310.32$ to $261.90$~ms) while \texttt{spatial\_reduction\_kernel} is unchanged at $2.62$~ms in both configurations, matching the GB10's pattern on a different microarchitecture. At the \emph{wall-clock} level the five configurations remain statistically hard to distinguish ($5{,}435$--$5{,}579\pm101$--$222$~ms, overlapping error bars) even though $32{\times}8$ nominally wins both metrics here; the kernel-level advantage is only cleanly visible via CUDA-event profiling, reinforcing why Section~\ref{sec:methodology}'s instrumentation matters. \subsection{Non-Unified Memory and FP64 Precision}
This platform's CPU/GPU memory is physically separate (64~GB DDR vs. 24~GB GDDR6X over PCIe), unlike the GB10's unified LPDDR5x pool over NVLink-C2C~\cite{nvidiagracehopper2022}, a distinction that recent work on unified physical memory for accelerators is beginning to study directly~\cite{wahlgren2025upm}. Despite this, GPU V2's Layer~8 kernel ($360.92 \pm 7.22$~ms) is faster in absolute terms than the GB10's ($533.19 \pm 2.58$~ms). The per-platform breakdown in Table~\ref{tab:breakdown} lets us say why, and the answer is not a single effect. Discrete-GPU PCIe/DMA overhead is well documented for transfer-bound workloads~\cite{go2017apunet}, and it is visible here --- in-window residual is $36.5\%$ of the RTX 4090's event window against the GB10's $22.1\%$, and D2H is $4.74\times$ slower --- but it is outweighed twice over. The deconvolution runs $1.6\times$ faster on the RTX 4090, and the bandwidth-bound reduction runs $10.0\times$ faster because the private buffer fits in its L2 (Section~\ref{sec:breakdown}). So the discrete-memory penalty is real and measurable rather than absent; it is simply smaller than the compute and cache advantages at this payload size ($\approx$44~MiB), and we would expect the balance to shift with a working set that overflows the RTX 4090's L2.

The double-precision design choice (Section~\ref{sec:methodology}) has a real cost here: as a consumer GPU, the RTX 4090's FP64 throughput is architecturally $1/64$ of its FP32 throughput ($\approx 1.3$ vs. $\approx 82.6$ TFLOPS), so the $360.92$~ms optimal kernel time (Section~\ref{sec:rtx4090}) is achieved with its dominant compute resource largely idle; an FP32 implementation would plausibly be substantially faster, at the cost of weakening bit-exactness to a numerical-tolerance claim. The GB10's datacenter-class GPU has a much smaller FP64:FP32 gap, so this trade-off is less severe there (not separately quantified). See Section~\ref{sec:limitations} for the FP32 ablation this motivates.

\section{Limitations and Future Work}
\label{sec:limitations}
Ordered roughly by priority:
\begin{itemize}
    \item No competitive GPU baseline: V2 is compared only against CPU implementations, not alternatives (\texttt{atomicAdd} accumulation, an output-stationary gather kernel, or cuDNN, Section~III-B). This is now the largest gap in the evaluation.
    \item Cache behaviour inferred, not measured: our explanation for the $10\times$ reduction-kernel gap --- that the $43.31$~MiB private buffer fits the RTX 4090's L2 but not the GB10's (Section~\ref{sec:breakdown}) --- rests on effective bandwidths, one of which exceeds DRAM peak. L2 hit-rate counters (\texttt{ncu}) would confirm it directly, and a working-set sweep across the L2 boundary would test the design rule we draw from it.
    \item Warp-alignment mechanism not directly profiled: the coalescing explanation (Section~III-B) is consistent with timing, and localized to \texttt{deconv\_kernel} as predicted, but still unverified by profiler load-efficiency counters; a sweep including non-aligned widths (e.g. $64{\times}4$) would isolate the effect further.
    \item In-window transfer not separated from launch gaps: after retracting the \texttt{h2d\_ms} reading (Section~\ref{sec:breakdown}), our host-to-device figure is an upper bound that still contains launch overhead and host-side padding. Pinned-memory or CUDA-stream instrumentation would separate them; the D2H measurement is unaffected.
    \item FP64 throughout, unquantified FP32 trade-off: no FP32 ablation was run to quantify the speedup vs. bit-exactness trade-off discussed in Section~\ref{sec:rtx4090}.
    \item RTX 4090 collapse not isolated from confounds: no \texttt{OMP\_PROC\_BIND}/\texttt{OMP\_PLACES} control experiment was run, so memory-bandwidth saturation, DVFS/thermal throttling, or false sharing remain possible alongside scheduler oversubscription.
    \item Reconstruction quality measured on one sequence at one scale factor (Section~\ref{sec:quality}), with a bicubic-downsampled input standing in for a natively high-resolution source; chroma is replicated rather than reconstructed, so the pipeline's perceptual quality is bounded by that, independent of Layer~8.
    \item Single test sequence/resolution: all results use the 150-frame QCIF-to-CIF Suzie sequence; higher resolutions (e.g. 1080p) would shift the compute-to-transfer ratio and, per the point above, push the private buffer past the RTX 4090's L2.
\end{itemize}

\section{Conclusion}

In this paper, we introduced a GPU Spatial Reduction framework for accelerating FSRCNN's Layer~8 deconvolution, evaluated on two architecturally distinct platforms. On both, V1 (CPU) and V2 (GPU spatial reduction) are bit-exact against a verified deterministic reference at every configuration tested, while V0's naive accumulation shows real, non-monotonic data-race corruption (as low as $13.8$~dB/$0.518$ SSIM on the GB10, and a near-undetectable $68.6$~dB/$0.99996$ on the RTX 4090; Fig.~\ref{fig:correctness}). On the GB10, the optimal $32{\times}8$ grid achieves $1.46\times$ speedup ($31.5$ FPS) over CPU V1's best correctness-verified configuration, and $3.84\times$ over the fastest bit-exact serial run (Section~\ref{sec:gb10-speedup}); the GPU Layer~8 kernels complete in $533.19 \pm 2.58$~ms. Cross-platform validation on a discrete-GPU desktop (Intel i9-14900K + RTX 4090, Section~\ref{sec:rtx4090}) confirms $32{\times}8$ remains fastest at the kernel level on a second GPU architecture, with GPU V2 outperforming that platform's best CPU configuration by up to $1.63\times$ despite non-unified memory; GPU V2's output is moreover bit-identical across both platforms directly (Section~\ref{sec:cross-arch-bitexact}), across different host ISAs and GPU architecture generations, while also surfacing a CPU thread-scheduling pathology independent of our GPU contribution.

Per-kernel profiling on both platforms (Section~\ref{sec:breakdown}) yields the paper's sharpest architectural result and also corrected an error in our own earlier instrumentation: what we had read as a large host-to-device transfer asymmetry was a host-side counter double-counting kernel-completion waiting, and we retract it. The genuine asymmetries run in opposite directions. Unified memory returns results $4.74\times$ faster (device-to-host, $3.46$ vs. $16.42$~ms), while the discrete GPU runs the bandwidth-bound reduction $10.0\times$ faster because its $72$~MB L2 holds the entire $43.31$~MiB private buffer that the GB10 must stream from LPDDR5x at $95\%$ of peak. The cost of determinism therefore depends less on the algorithm than on whether the privatization working set fits in last-level cache. Section~\ref{sec:limitations} lists the follow-up experiments needed to fully close out these findings.
